# S2-T02 - Хранилище hard state с fsync до ответа на RPC

- Этап: S2 - Raft: роли, term и выборы
- Статус: open
- Зависит от: `S2-T01` (тип `HardState` и контракт `IHardStateStore`), `S1-T09` (шов файловой системы, done)
- Спецификация этапа: `docs/stages/02 - Raft roles and elections.md`
- Гейт: `pwsh scripts/verify.ps1`

## Что сделать

Реализовать `HardStateStore` поверх `IStorageFileSystem`: атомарная запись пары `(CurrentTerm, VotedFor)` так,
чтобы оборванная запись не портила предыдущее состояние, и нормативный формат файла в `docs/formats/hard-state.md`.

## DoD (из плана)

Тест: рестарт после голосования не даёт проголосовать второй раз в том же term (инвариант R6).

## Правило, которое нельзя ослабить

**Persist before respond.** Запись с fsync уходит до отправки ответа на RPC. Это касается не только согласия:
рост term при получении сообщения с бо́льшим term - тоже durable изменение (чек-лист `R2`, вопрос 1).

## Формат (до кода - `docs/formats/hard-state.md`)

Побайтово: magic, версия формата, длина записи, `sequence`, `currentTerm`, `votedFor` (нулевой маркер = не
голосовал), CRC32C, правило совместимости версий. Файла нет → начальное состояние (`term = 0`, `votedFor = null`),
а не ошибка. Порча обоих слотов → структурный отказ старта, а не «начать с нуля»: иначе R6 нарушается молча.

Два слота фиксированной длины (`[header][slot0][slot1]`) вместо temp+rename: пишем в слот с меньшим `sequence`,
fsync, читаем валидный слот с большим `sequence`. Сбой посреди записи не портит прошлый слот, размер файла
фиксирован форматом. Альтернатива (temp + rename + fsync каталога) с `S1-T09` технически доступна - если она
выбирается, это фиксируется в ADR с ценой (шов уже расширен `RenameAsync`/`FlushDirectoryAsync`).

## Что уже есть под руками

- `IStorageFileSystem`: `CreateAsync`, `OpenReadAsync`, `OpenAppendAsync`, `ListFilesAsync`, `TruncateAsync`,
  `DeleteAsync`, `RenameAsync`, `FlushDirectoryAsync`; `FakeStorageFileSystem` умеет падать на заданной операции.
- `CrashHarness` (`tests/RaftBroker.CrashHarness`) умеет `torn-frame`, `torn-header`, `snapshot-mid-write`:
  добавить режим `hard-state` (убить процесс между записью слота и fsync).
- `docs/formats/snapshot.md` - образец нормативного документа формата.

## Как проверять

- Crash-тест на реальном рестарте процесса: голос отдан → kill → старт → второй голос в том же term невозможен.
- Крах между записью слота и fsync → читается предыдущий слот (старый term); два разных голоса в одном term
  невозможны.
- CRC не сходится в одном слоте → берётся другой; ни в одном → структурный отказ.
- Рост term без голоса (step down) переживает рестарт.
- Пустой каталог → `term = 0`, `votedFor = null`.
- Сквозной тест на реальном диске во временном каталоге (по образцу `S1-T05`).

## Ловушки

- Не переиспользовать формат сегмента журнала: у hard state нет индексов и непрерывности, зато есть два слота.
- `Flush(flushToDisk: true)` создаёт файл, если его нет; «записать атомарно поверх» этим не выражается.
- Порядок «закрыть писателя, потом переименовать/удалить» (ADR `0007`, `0008`): на Windows открытый файл не удаляется.
- Ветки «нет файла», «битый слот», «оба слота битые», «fsync упал» - каждая с тестом, иначе покрытие 98.5% не держится.

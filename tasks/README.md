# Задачи raft-broker

Единственный список работ по проекту: 9 этапов, 85 задач, идентификаторы `S<этап>-T<номер>`.
Список перенесён из хранилища владельца 2026-10-22; там остались обоснования, история решений и ревью-отчёты,
но не задачи. Если реализация требует заглянуть в хранилище, задача описана плохо - это дефект задачи, а не порядка.

## Как это ведётся

1. Идентификатор присваивается один раз и не меняется; закрытая задача не перенумеровывается и не переписывается.
2. Статусы: `open`, `in-progress`, `done` с хешем коммита. Задача закрыта, когда выполнен её DoD, `scripts/verify.ps1`
   зелёный и есть коммит с id в subject.
3. Одна задача - один коммит или короткая серия. Subject начинается с id: `S1-T06: ...`.
4. Доработка уже закрытой задачи - отдельный коммит с тем же id и пометкой `follow-up` или `fix`; история не
   переписывается. Так уже было: `S0-T04 follow-up`, `S0-T08 fix`.
5. Закрывая задачу, обновите её строку в этой таблице (статус и хеш коммита) тем же коммитом.
6. Тело задачи (`tasks/S1-T06-log-store.md`) пишется, когда DoD перестаёт влезать в строку индекса; ссылка на тело
   ставится в колонке «Задача».
7. Идея не становится задачей сама: номер выдаёт владелец, свободный номер - следующий в своём этапе.
8. Спецификация этапа пишется до кода. Спека переезжает в репозиторий, когда этап стартует (`docs/stages/`);
   сейчас здесь только S1, спека S0 осталась в хранилище как история закрытого этапа.
9. Этап закрывается ревью-гейтом `R<этап>`: владелец читает код и тесты этапа и отвечает на чек-лист из
   спецификации. Гейт проставляет владелец, не агент.
10. Инварианты проекта и их привязка к тестам: `docs/invariants.md`.

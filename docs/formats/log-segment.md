# Формат сегмента журнала (`log-segment`)

- **Статус:** нормативный документ, версия формата `1`
- **Задача:** `S1-T01` — спецификация формата сегмента
- **Обоснование решений:** [`docs/adr/0003-log-segment-format.md`](../adr/0003-log-segment-format.md)
- **Реализуют:** `S1-T02` (кодек), `S1-T03` (запись и rollover), `S1-T04` (чтение), `S1-T05` (recovery), `S1-T06`/`S1-T07` (индекс и восстановление), `S1-T09` (снапшот — отдельный формат), `S1-T10` (компакция)

Документ описывает байты одного файла сегмента журнала Raft. Всё, что не описано здесь явно, форматом не является: реализация, делающая вывод, не следующий из этого текста, считается дефектом. Данных, не описанных как поле, в файле нет — «резерв на будущее» в формат не заложен намеренно.

## 1. Термины

| Термин | Значение |
|---|---|
| Сегмент | Один файл `*.seg` в каталоге лога. Append-only: после закрытия не переписывается и не переименовывается. |
| Заголовок | Первые 30 байт файла (§3). |
| Фрейм | Единица записи журнала. Единственный элемент, дописываемый в конец файла (§4). |
| `baseIndex` | Индекс журнала первой записи сегмента. Хранится в заголовке и в имени файла. |
| Запечатанный сегмент | Сегмент, у которого есть файл-преемник (сегмент с большим `baseIndex`). Дописывать его нельзя. |
| Последний сегмент | Сегмент с наибольшим `baseIndex` в каталоге. Только он может быть неполным. |
| Валидный префикс | Наибольшая последовательность фреймов от начала области фреймов, каждый из которых полон и проходит проверку CRC (§9). |
| Torn write | Обрыв записи: хвост файла содержит байты незавершённого фрейма (§9.2). |
| Порча (corruption) | Повреждение, при котором после повреждённого места в логе есть валидные данные (§9.4). Автоматическое усечение запрещено. |

**Порядок байт: little-endian для всех целых чисел**, без исключений. Все смещения — от начала файла, если не сказано иное. Выравнивания нет: многобайтовые поля читаются по смещению, не кратному размеру поля.

## 2. Раскладка файла

```
+---------------------------+
| header  30 байт           |   §3
+---------------------------+
| frame[0]                  |   index = baseIndex
+---------------------------+
| frame[1]                  |   index = baseIndex + 1
+---------------------------+
| ...                       |
+---------------------------+
| frame[k]                  |   последний фрейм; может быть оборван
+---------------------------+
```

Размер файла: `30 + сумма размеров фреймов`. Больше в файле нет ничего: ни выравнивающих байтов, ни завершающей подписи.

## 3. Заголовок сегмента (30 байт)

| Смещение | Размер | Поле | Тип | Значение |
|---|---|---|---|---|
| 0 | 8 | `magic` | ASCII | `RBSEGLOG` — константа семейства файлов |
| 8 | 2 | `formatVersion` | u16 | `1` в этой версии формата |
| 10 | 8 | `baseIndex` | i64 | Индекс первой записи сегмента, `>= 1` |
| 18 | 8 | `createdAtUnixMs` | i64 | Момент создания файла, Unix-мс. Информационное поле |
| 26 | 4 | `headerCrc32c` | u32 | CRC32C (§5) по байтам `[0, 26)` |

Правила:

1. `magic` **не содержит версию**. Версия живёт ровно в одном месте — в поле `formatVersion`. Две копии номера версии разъедутся, поэтому в магии её нет (расхождение с эскизом этапа, где магия была `RBSEG001`; причина — в ADR 0003).
2. `formatVersion` читается первым. Неизвестная версия — отказ, а не «попробуем прочитать как получится» (§10).
3. `createdAtUnixMs` не влияет ни на одно решение о корректности и не участвует в сравнении или хешировании содержимого. Это единственное недетерминированное поле формата, и оно только справочное.
4. `headerCrc32c` считается по всем полям заголовка, кроме самого CRC. Он позволяет детерминированно отличить «не наш файл» от «наш файл с повреждённым заголовком» без эвристик.
5. `baseIndex` обязан совпадать с числом, закодированным в имени файла (§7). Расхождение — порча.

## 4. Фрейм записи

`N` — длина `payload`.

| Смещение от начала фрейма | Абсолютное смещение первого фрейма | Размер | Поле | Тип |
|---|---|---|---|---|
| 0 | 30 | 4 | `frameLength` | u32 |
| 4 | 34 | 1 | `recordType` | u8 |
| 5 | 35 | 8 | `term` | i64 |
| 13 | 43 | 8 | `index` | i64 |
| 21 | 51 | `N` | `payload` | байты |
| 21 + N | 51 + N | 4 | `crc32c` | u32 |

Размеры и правила:

1. `frameLength = 17 + N` — длина части фрейма от `recordType` до конца `payload` включительно. Поля `frameLength` и `crc32c` в неё не входят.
2. Размер фрейма на диске: `4 + 17 + N + 4 = 25 + N` байт. `N = 0` допустим.
3. Границы payload: `0 <= N <= 1 048 576` (1 МиБ). Отсюда `17 <= frameLength <= 1 048 593`. Запись payload больше 1 МиБ отвергается **на записи** понятной ошибкой (`S1-T02`, `S1-T03`), а не обрезается. На чтении `frameLength` вне этих границ — порча (§9.4): корректный писатель такого фрейма создать не мог.
4. `frameLength = 0` запрещено (частный случай правила 3).
5. `term >= 0`, `index >= 1`.
6. `crc32c` считается по байтам `recordType .. payload`, то есть по `frameLength` байтам, начиная со смещения 4 фрейма. Поле `frameLength` в CRC не входит: позиция CRC и так вычисляется из него.
7. **Payload непрозрачен.** Хранилище не разбирает его ни для одного типа записи, включая `config`. Обязательство: байты `payload` возвращаются читателю ровно такими, какими были записаны, включая нулевую длину.

Инварианты последовательности фреймов:

1. Фрейм с номером `k` (нумерация с нуля от начала области фреймов) обязан иметь `index = baseIndex + k`. Дыр, повторов и перестановок нет.
2. `index` строго возрастает на 1 внутри сегмента и продолжается в преемнике: `baseIndex` следующего сегмента равен последнему `index` предыдущего плюс 1.
3. `term` не убывает вдоль журнала (свойство Raft: терм лидера не уменьшается). Убывание — порча, а не «нормальный лог».
4. Нарушение любого из этих инвариантов при чтении — порча (§9.4), а не частичный успех.

## 5. CRC32C

Контрольная сумма — **CRC-32C (Castagnoli)**, та же, что в iSCSI (RFC 3720), метаданных ext4 и журнале Kafka.

| Параметр | Значение |
|---|---|
| Полином (normal) | `0x1EDC6F41` |
| Полином (reflected) | `0x82F63B78` |
| Начальное значение (`init`) | `0xFFFFFFFF` |
| Отражение входа/выхода (`refin`/`refout`) | да / да |
| Финальный XOR (`xorout`) | `0xFFFFFFFF` |
| Контрольное значение `CRC32C("123456789")` | `0xE3069283` |

Контрольные векторы (обязаны пройти в тестах `S1-T02`; вычислены независимой реализацией, а не взяты из кода проекта):

| Вход | CRC32C |
|---|---|
| пустой ввод | `0x00000000` |
| ASCII `123456789` | `0xE3069283` |
| 32 байта `0x00` | `0x8A9136AA` |
| 32 байта `0xFF` | `0x62A8AB43` |
| байты `0x00, 0x01, ... 0x1F` | `0x46DD794E` |

Почему не `System.IO.Hashing`: в пакете версии 9.0.0 (сборки `lib/net8.0` и `lib/net9.0`) есть только `Crc32`, `Crc64`, `XxHash32`, `XxHash64`, `XxHash3`, `XxHash128` и базовый `NonCryptographicHashAlgorithm`; типа `Crc32C` там нет (проверено чтением состава пакета, см. ADR 0003). Реализация живёт в репозитории и обязана совпадать с векторами выше — формат определяет значения CRC, а не способ их вычисления. Аппаратное ускорение (`Sse42.Crc32`/`Arm.Crc32`) допустимо как оптимизация, но только с тестом, доказывающим совпадение с табличной реализацией на всех векторах и на случайных входах.

CRC считается от фактических байтов на диске. Это значит: любое изменение формата фрейма меняет значения CRC и обязано сопровождаться повышением `formatVersion` (§10).

## 6. Типы записей

| Значение | Имя | Payload | Кто создаёт | Кто читает |
|---|---|---|---|---|
| `0x00` | запрещено | — | — | Всегда порча (§9.4) |
| `0x01` | `command` | Команда state machine. Непрозрачные байты | Лидер при предложении клиента | Apply-loop |
| `0x02` | `noop` | Пусто (`N = 0`) | Лидер при входе в должность в новом терме | Apply-loop |
| `0x03` | `config` | Команда изменения состава кластера. Непрозрачные байты | Лидер при изменении состава | Apply-loop (регистр конфигураций) |
| `0x04 .. 0xFF` | не определено | — | — | **Отказ**: неизвестный тип нельзя ни применить, ни молча пропустить |

Правила:

1. Таблица закрыта. Читатель, встретивший неизвестный `recordType`, обязан отказать с указанием позиции фрейма: пропустить запись нельзя (её надо применить), а применить неизвестное нельзя. Это и есть правило совместимости из §10.
2. `noop` с непустым payload — порча: тип определён как запись без полезной нагрузки.
3. Хранилище не проверяет семантику payload типов `command` и `config` и не имеет о них мнения. Тип нужен, чтобы apply-loop мог отличить команду от изменения состава, и чтобы компакция и снапшоты не теряли незнакомые ей записи (§10).
4. Значения закреплены навсегда: переиспользовать номер типа под другую семантику нельзя. Отменённый тип помечается как запрещённый, а не отдаётся под новое значение.

## 7. Каталог и имена файлов

- Сегменты лежат в каталоге `<data-dir>/log/`. Другие файлы в этом каталоге запрещены: посторонний файл — ошибка конфигурации или потерянный артефакт, и о нём нужно сказать, а не проигнорировать его молча.
- Имя файла: `{baseIndex:D20}.seg` — `baseIndex`, записанный **20 десятичными цифрами** (`0`..`9`, инвариантная культура, ASCII), затем `.seg`. Пример: запись с индексом `1` — файл `00000000000000000001.seg`.
- 20 цифр выбраны так, чтобы строка имени имела постоянную длину и лексикографический порядок имён совпадал с числовым порядком индексов (`long.MaxValue` — 19 цифр).
- Сегмент **не переименовывается** после создания. Компакция удаляет файлы целиком, но не меняет их имена.
- Файлы в каталоге обязаны образовывать непрерывный диапазон: `baseIndex[i+1] == lastIndex(segment[i]) + 1`. Разрыв, перекрытие или несовпадение имени с `baseIndex` заголовка — порча. Единственное допустимое «начало не с единицы» — компакция, удалившая префикс сегментов (`S1-T10`): тогда первый файл начинается с индекса, не меньшего, чем граница снапшота.

## 8. Размер сегмента и rollover

- Номинальный максимум сегмента: **64 МиБ = 67 108 864 байт** (закрывает открытое решение 1 этапа; обоснование — ADR 0003). Значение конфигурируемо, но **формат от него не зависит**: читатель обязан принимать сегмент любого размера.
- Rollover выполняется **только на границе записи**: фрейм никогда не разрывается между двумя сегментами.
- Решение о rollover принимается до записи фрейма: если текущий сегмент непуст и `текущий размер + размер фрейма > максимум`, создаётся новый сегмент, а фрейм пишется уже в него.
- Пустой сегмент (создан, но ни одного фрейма ещё нет) допустим только как последний. Не последний сегмент обязан содержать хотя бы один фрейм.
- `baseIndex` нового сегмента — индекс того фрейма, ради которого произошёл rollover.
- Один фрейм больше максимального размера сегмента — программная ошибка (при лимите payload 1 МиБ недостижима, но проверяется).
- **Порядок операций при rollover** (обязателен для `S1-T03`): (1) flush и fsync текущего сегмента; (2) создать новый файл, записать заголовок, fsync заголовка; (3) записать фрейм. Первый шаг обязателен: иначе запечатанный сегмент мог бы остаться с неотфлашенным хвостом, а §9.4 требует, чтобы запечатанный сегмент всегда был полон. После шага (2) предыдущий сегмент считается запечатанным.

## 9. Целостность: torn write, оборванное создание, порча

### 9.1 Что проверяется

При чтении проверяются, по порядку:

1. размер файла не меньше заголовка (30 байт);
2. `magic`, `formatVersion`, `headerCrc32c`;
3. `baseIndex >= 1` и совпадение с именем файла;
4. для каждого фрейма: достаточно ли байтов, `frameLength` в границах `[17, 1 048 593]`, `recordType` из §6, `term >= 0`, `index >= 1`, `index` монотонен на 1, `term` не убывает, `crc32c` совпадает.

Нарушение правил 1–3 — уровень сегмента; нарушение правила 4 — уровень фрейма. Разные уровни дают разное поведение.

### 9.2 Torn write (обрыв записи в хвосте)

Torn write — это ситуация, когда последний фрейм дописан не полностью. Признаки:

- в файле меньше 4 байт от начала фрейма, либо
- прочитанный `frameLength` таков, что `frameLength + 4` байт до конца файла не достаёт, либо
- байты есть, но `crc32c` не совпадает, и **после этого фрейма в файле нет ни одного полного CRC-валидного фрейма** (проба продолжения, §9.5 шаг 5).

Поведение: валидный префикс сохраняется, хвост от начала повреждённого фрейма **усекается** до последней валидной записи. Усечение разрешено **только для последнего сегмента**: запечатанный сегмент не может быть оборван, потому что writer fsync-ает его перед созданием преемника (§8). Усечение — не «тихая починка»: факт, позиция и число отброшенных байт попадают в отчёт о восстановлении. Записи из отброшенного хвоста не могли быть подтверждены клиенту, потому что подтверждение выдаётся только после fsync (`S1-T03`), — именно на этом и держится право их отбросить (инвариант R6, тесты `S1-T05`).

### 9.3 Оборванное создание сегмента

Заголовок записывается и fsync-ается до первого фрейма (§8, шаг 2). Поэтому сегмент, у которого заголовок нечитаем, не может содержать подтверждённых записей — но только если он действительно не содержит фреймов.

Правило:

- Файл короче 30 байт и это последний сегмент — оборванное создание: файл удаляется (или игнорируется), в отчёт попадает позиция. Запечатанный сегмент короче заголовка — порча.
- Файл длиной >= 30 байт с неверным `magic`/`formatVersion`/`headerCrc32c` и это последний сегмент — **отказ от старта с диагностикой**, а не удаление: наличие валидного фрейма на смещении 30 сделать вывод об отсутствии данных не позволяет, а молча удалить сегмент с возможными подтверждёнными записями нельзя. Решение сознательно выбирает недоступность вместо потери данных.

### 9.4 Порча (corruption)

Порчей считается любое нарушение, при котором после повреждённого места в логе есть валидные данные, а именно:

- неверный `magic`, неизвестная `formatVersion`, несовпадение `headerCrc32c` (§9.3 — исключение только для короткого последнего файла);
- любое нарушение в **запечатанном** сегменте: он обязан разбираться от заголовка до конца файла ровно на границе фрейма, без остатка;
- нарушение инвариантов последовательности (§4): дыра, повтор, скачок `index`, убывание `term`;
- `recordType`, которого нет в §6; `noop` с непустым payload; `frameLength` вне границ;
- разрыв или перекрытие диапазона сегментов в каталоге (§7).

Поведение: **отказ с диагностикой** (файл, смещение, что именно не сошлось). Автоматическое усечение здесь запрещено: иначе молча теряется закоммиченная история. Восстановление — ручное действие оператора, и оно не описано этим документом.

### 9.5 Алгоритм чтения журнала (восстановление по документу, без кода)

1. Перечислить `<data-dir>/log/*.seg`. Любой другой файл в каталоге — ошибка.
2. Разобрать `baseIndex` из имён, отсортировать по `baseIndex` (порядок имён совпадает с числовым порядком, §7). Сегмент с именем, из которого индекс не разбирается, — ошибка.
3. Для очередного сегмента в порядке возрастания проверить заголовок:
   - файл короче 30 байт — последний сегмент: отбросить (§9.3); запечатанный: порча;
   - `magic`, `formatVersion` или `headerCrc32c` не сошлись — последний: отказ (§9.3); запечатанный: порча;
   - `baseIndex < 1` или `baseIndex` не равен ожидаемому (`1` для первого, иначе `lastIndex` предыдущего `+ 1`) — порча.
4. Сканировать фреймы от смещения 30, пока они полны и валидны, отслеживая ожидаемый `index` и предыдущий `term`:
   - от начала фрейма осталось меньше 4 байт — валидный префикс кончился;
   - `frameLength` вне `[17, 1 048 593]` — в последнем сегменте перейти к шагу 5, в запечатанном — порча;
   - `frameLength + 4` байт до конца файла не достаёт — валидный префикс кончился (сегмент обязан быть последним, иначе порча);
   - `recordType` не из §6, `index` не равен ожидаемому или `term` меньше предыдущего — в последнем сегменте перейти к шагу 5, в запечатанном — порча;
   - `crc32c` не совпал — перейти к шагу 5;
   - фрейм валиден — запомнить `index` и `term` и продолжить со следующего фрейма.
5. **Проба продолжения** — только для последнего сегмента; она отличает порчу от torn write. Пусть `p` — смещение первого невалидного фрейма, `L` — его `frameLength`, если 4 байта присутствуют и `L` в границах. Если на смещении `p + 4 + L + 4` находится полный CRC-валидный фрейм, повреждение находится не в хвосте, а в середине: **порча, отказ**. Иначе (в том числе если `L` прочитать нельзя или он вне границ) валидный префикс кончается на `p`, и хвост `[p, конец файла)` отбрасывается как torn write.
6. Для запечатанного сегмента дополнительно потребовать, чтобы последний валидный фрейм кончался ровно на конце файла: остаток байтов — порча.
7. Перейти к шагу 3 для следующего сегмента. Первая же обнаруженная порча прекращает чтение с ошибкой; отброшенные хвосты последнего сегмента в ошибку не превращаются, но попадают в отчёт.

Результат: непрерывный валидный префикс журнала, `LastIndex`, `LastTerm` и отчёт о восстановлении (что усечено, что отброшено). Реализация — `S1-T04`, `S1-T05`, `S1-T07`.

### 9.6 Границы применимости

Правило §9.5 различает torn write и порчу по признаку «есть ли валидные данные после повреждения». Если повреждено **и** поле `frameLength`, и содержимое фрейма в середине последнего сегмента, проба продолжения может не найти следующий фрейм и принять порчу за torn write. Модель отказов проекта (раздел «Модель отказов» в спецификации проекта `raft-broker`) рассматривает только частичное и обнаружимое повреждение; сценарий «сначала испорчена длина, а файл после этого остался целым» в неё не входит. Остаточный риск зафиксирован явно, и `S8-T03` обязан проверять, что хаос-прогон не приводит к тихой потере подтверждённых записей.

## 10. Совместимость и миграция

`formatVersion` повышается, если меняется **что угодно** из перечисленного:

- раскладка или размер заголовка, состав полей фрейма;
- границы или смысл `frameLength`;
- область действия CRC (какие байты в неё входят) или сам алгоритм;
- порядок байт;
- смысл уже занятых значений `recordType` или инварианты `index`/`term`;
- правило именования файлов и порядок сегментов.

Правила:

1. Читатель принимает только известные ему версии. Неизвестная версия — отказ с указанием файла и версии. Вариант «попробуем прочитать как получится» запрещён: неверно понятый журнал хуже, чем отказ старта.
2. Внутри версии `1` forward-compatible расширений нет: неизвестный `recordType` отвергается (§6), неизвестная версия отвергается. Значит, любое расширение — новая версия формата, а не «добавили тип и поехали».
3. Номера `recordType` не переиспользуются никогда: отменённый тип остаётся запрещённым, а не занимается под новую семантику.
4. Сегменты разных версий в одном каталоге лога запрещены. Переход v1 → v2 — это явная офлайн-миграция (перезапись лога инструментом, отдельная задача при необходимости), а не постепенное вытеснение. Откат (v2 → v1) невозможен без обратной миграции.
5. `headerCrc32c` и `magic` не «лечатся»: сегмент с повреждённым заголовком не восстанавливается, а отвергается (§9.3, §9.4).

Это и есть правило из цели этапа: **формат не меняется без миграции**. Любая правка кодека, меняющая байты на диске, обязана либо уложиться в ту же версию (и тогда она — дефект), либо поднять `formatVersion` и принести миграцию.

## 11. Какое правило какой задачей проверяется

| Правило | Задача | Тест |
|---|---|---|
| Заголовок и фрейм читаются/пишутся побайтово, round-trip | `S1-T02` | property-based на 10 000 случайных записей |
| Битая `crc32c` отвергается | `S1-T02` | тест на порченом фрейме + контрольные векторы CRC |
| `frameLength` вне границ, неизвестный `recordType`, `noop` с payload — отказ | `S1-T02`, `S1-T05` | таблица негативных случаев |
| Границы сегментов, пустой сегмент, запись ровно в конец | `S1-T04` | модульные тесты |
| Torn write на каждом байте последнего фрейма, детерминированное усечение | `S1-T05` | crash-тест с реальным убийством процесса |
| Порча в середине запечатанного сегмента — отказ без усечения | `S1-T05`, `S1-T06` | тест на порче с валидными данными после неё |
| Непрерывность диапазона сегментов, разрыв — отказ | `S1-T06`, `S1-T07` | модульный тест на дыре в именах |
| `LastIndex`/`LastTerm` после рестарта | `S1-T07` | тест рестарта |
| Компакция не удаляет записи ниже снапшота и не создаёт дыру | `S1-T10` | интеграционный тест с крахом в каждой точке |

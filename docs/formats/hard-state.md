# Формат файла hard state (версия 1)

Нормативное описание файла, в котором узел хранит `currentTerm` и `votedFor`.
Реализация: `src/RaftBroker.Storage/HardState/` (`HardStateFormat`, `HardStateRecordCodec`, `HardStateStore`).
Решения и их обоснование: ADR `0014-hard-state-file.md`. Задача: `S2-T02`.

## 1. Что это за файл

Единственное, что узел обязан помнить между рестартами сверх журнала: **какой term он считает текущим
и за кого в нём голосовал**. Потеря этих двух полей ломает R6 («подтвердил - переживает крах»):
узел, забывший голос, голосует второй раз в том же term за другого кандидата, и в кластере
появляются два лидера в одном term.

Запись hard state происходит **до** ответа на RPC (`RequestVote`, `PreVote`) и до отправки
`AppendEntries` с новым term. Это правило этапа S2 (`docs/stages/02 - Raft roles and elections.md`,
правило 1), а не деталь хранилища.

## 2. Раскладка

Файл - **последовательность самодостаточных записей** без общего заголовка. Записи только
дописываются в конец; текущее состояние - последняя запись, у которой сошёлся CRC.

```
[запись 1][запись 2]...[запись N]
```

Отдельного заголовка файла нет намеренно: заголовок не сообщает ничего о состоянии, но его
порча означала бы потерю всего файла. У записи есть своя сигнатура, поэтому файл читается
сканированием с начала без внешних метаданных.

### 2.1. Запись

| Смещение | Размер | Поле | Смысл |
|---------:|-------:|------|-------|
| 0 | 8 | `magic` | `"RBHSREC1"` (ASCII, big-endian порядок байтов как в литерале) |
| 8 | 8 | `sequence` | номер записи, `int64` little-endian, начинается с 1 и растёт на 1 |
| 16 | 8 | `currentTerm` | `int64` little-endian, `>= 0` |
| 24 | 2 | `votedForLength` | длина `votedFor` в байтах UTF-8, `uint16` little-endian, `0..512` |
| 26 | `votedForLength` | `votedFor` | идентификатор узла в UTF-8; пусто = голос не отдан |
| 26 + `votedForLength` | 4 | `crc32c` | CRC-32C всех предыдущих байтов записи, `uint32` little-endian |

Размер записи: `30 + votedForLength` байт (`HeaderSize = 26`, `CrcSize = 4`).

`votedForLength = 0` означает «в этом term голос не отдан»; отдельного признака нет, потому что
пустой идентификатор узла невозможен (`NodeId` требует непустую строку). Предел 512 байт - это
128 символов идентификатора (`Guard.MaxIdentifierLength`) в худшем случае UTF-8.

### 2.2. Пример

Узел `node-2` в term 5 проголосовал за `node-1` (6 байт):

```
52 42 48 53 52 45 43 31   "RBHSREC1"
01 00 00 00 00 00 00 00   sequence = 1
05 00 00 00 00 00 00 00   currentTerm = 5
06 00                     votedForLength = 6
6E 6F 64 65 2D 31         "node-1"
3F 8A 11 D4               crc32c (пример условный)
```

## 3. Чтение

1. Файла нет - начальное состояние: `currentTerm = 0`, `votedFor = null` (узел ещё ни за кого
   не голосовал). Файл создаётся пустым при первой загрузке.
2. Файл есть - сканирование с начала: читается заголовок (26 байт), по `votedForLength`
   определяется размер записи, запись читается целиком и проверяется CRC. Валидная запись
   запоминается как текущее состояние, сканирование продолжается.
3. Состояние - последняя валидная запись. `sequence` используется только для диагностики:
   порядок в файле и есть порядок записи.

### 3.1. Обрыв и порча различаются

| Что видно в файле | Трактование |
|-------------------|-------------|
| осталось меньше 26 байт до конца файла | обрыв: хвост усекается |
| заголовок цел, но запись целиком не помещается в файл | обрыв: хвост усекается |
| сигнатура не совпадает у записи, которая целиком помещается в файл | **порча**: `InvalidDataException` |
| `votedForLength > 512` | **порча**: `InvalidDataException` |
| CRC не сходится у целой по длине записи | **порча**: `InvalidDataException` |
| `currentTerm < 0` | **порча**: `InvalidDataException` |
| `votedFor` не является идентификатором узла | **порча**: `InvalidDataException` |

Усечение хвоста безопасно: последняя валидная запись была сброшена на устройство до того, как
`WriteAsync` вернул управление, поэтому подтверждённое состояние не теряется.

Порча внутри файла не «откатывается» к предыдущей записи. Откат означал бы, что узел может
забыть собственный голос и проголосовать второй раз в том же term - ровно то, от чего этот
файл защищает. Вместо этого узел не стартует и сообщает об ошибке.

## 4. Запись

1. Дописать запись в конец файла (append).
2. `fsync` файла - до возврата управления.
3. Обновить состояние в памяти только после успешного `fsync`.

Отдельный `fsync` каталога не нужен: файл hard state создаётся **до** первой записи и дальше
не переименовывается, поэтому после `fsync` файла его содержимое на устройстве. Создание файла
(первый запуск) - единственный момент, когда нужен каталог; потеря созданного, но пустого файла
после краха безвредна: это то же начальное состояние.

Если запись или `fsync` не удались, вызывающий получает исключение, состояние в памяти остаётся
прежним, а следующий append сначала усекает файл до последней подтверждённой длины. Иначе
недописанная запись оказалась бы в середине файла и чтение остановилось бы на порче при
рестарте. Запись, на которой упал `fsync`, не принимается за состояние даже если физически
оказалась на диске целиком: подтверждённой она не была, и полагаться на неё после краха нельзя.

## 5. Рост файла и совместимость

Запись добавляется на каждый новый term и на каждый голос; в установившемся кластере это
единицы байтов на событие, а не поток. Компакции у файла нет - это осознанный компромисс
(ADR `0014`): она потребовала бы либо переименования с заменой, которого нет в
`IStorageFileSystem`, либо второго формата. Если измерения покажут заметный рост (тысячи
term в сутки на узел), появится компакция отдельной задачей - формат к ней готов: достаточно
переписать последнюю валидную запись в новый файл.

Правила совместимости:

* `magic` содержит версию (`RBHSREC1`); файл другой версии не читается и не «угадывается».
* Новые поля добавляются только в конец записи, перед CRC; старые смещения не меняются.
* Поле не удаляется и не меняет смысл: `votedForLength = 0` навсегда означает «не голосовал».
* Смена версии - новый `magic`, миграция отдельной задачей; тихого «прочитать как получится» нет.

## 6. Чего формат не делает

* Не хранит журнал, снапшот и commit index: журнал - отдельные сегменты (`docs/formats/log-segment.md`),
  снапшот - `snapshot-{index:D20}.snap` (`docs/formats/snapshot.md`), `commitIndex` после рестарта
  восстанавливается как `snapshotIndex` (S3).
* Не хранит конфигурацию кластера: она часть журнала, а не hard state.
* Не дедуплицирует записи и не сжимает их.
* Не даёт транзакций: одна запись - один переход состояния.

# Формат файла снапшота, версия 1

Нормативный документ. Реализация: `src/RaftBroker.Storage/Snapshot`. Решения и их причины:
`docs/adr/0012-snapshot-file-and-atomic-publication.md`. Формат журнала, с которым снапшот
составляет пару, - `docs/formats/log-segment.md`.

## 1. Назначение

Снапшот - это состояние приложения на момент `lastIncludedIndex` вместе с двумя числами,
которые нужны Raft: индекс и терм последней вошедшей записи. Файл самодостаточен: узел,
имеющий только снапшот и хвост журнала, восстанавливается без чтения сжатой части
(инвариант Q7).

Байты состояния хранилище не толкует: их пишет и читает приложение (`StateMachine`).
Хранилище отвечает за то, чтобы файл либо целиком валиден, либо не существует.

## 2. Имя файла

```
snapshot-{lastIncludedIndex:D20}.snap
```

- `{lastIncludedIndex:D20}` - индекс последней вошедшей записи, ровно 20 десятичных цифр
  (как у сегментов журнала, §7 `log-segment.md`): постоянная длина даёт лексикографический
  порядок, совпадающий с числовым.
- Суффикс `.snap`. Временный файл в момент записи - то же имя плюс `.tmp`:
  `snapshot-{lastIncludedIndex:D20}.snap.tmp`.
- Индекс больше нуля. Снапшот на индексе 0 не существует: пустой журнал нечего сжимать.
- Другие имена файлов в каталоге снапшотов не считаются снапшотами, и хранилище их не удаляет.

## 3. Раскладка файла

| Смещение | Размер | Содержимое |
|---|---|---|
| 0 | 48 | заголовок (§4) |
| 48 | `stateLength` | байты состояния приложения |
| 48 + `stateLength` | 0 | конец файла |

Размер файла обязан быть ровно `48 + stateLength`. Хвост после состояния - порча: он означает,
что файл дописали в обход формата, и читать из него что-либо нельзя.

В отличие от сегмента журнала, внутри снапшота нет последовательности записей: непрерывности
индексов внутри одного файла не существует по построению (снапшот - одна точка `lastIncludedIndex`).
Следствие: `lastIncludedIndex` следующего снапшота обязан быть больше предыдущего, и это
обеспечивает вызывающий (журнал не отдаёт снапшот назад, `ILogStore.CompactAsync`), а хранилище
только проверяет, что метаданные файла совпадают с предполагаемыми.

## 4. Заголовок

Порядок байтов - little-endian, как и в журнале (`log-segment.md` §3).

| Смещение | Размер | Поле | Смысл |
|---|---|---|---|
| 0 | 8 | `magic` | ASCII `RBSNAP01`: имя формата и версия в одном месте |
| 8 | 8 | `lastIncludedIndex` | индекс последней записи, вошедшей в снапшот (u64, больше нуля) |
| 16 | 8 | `lastIncludedTerm` | терм этой записи (u64, может быть 0 у пустого журнала) |
| 24 | 8 | `createdAtUnixMs` | момент создания, мс от эпохи (i64) |
| 32 | 8 | `stateLength` | длина состояния в байтах (u64) |
| 40 | 4 | `stateCrc32C` | CRC-32C байтов состояния (§5) |
| 44 | 4 | `headerCrc32C` | CRC-32C байтов 0..43 (§5) |

`HeaderSize = 48`.

Магия несёт версию (`RBSNAP01`), а отдельного поля версии нет: у журнала версия живёт
в заголовке, но у снапшота она нужна только для того, чтобы отличить чужой файл от своего,
и одна магия читается проще, чем магия плюс поле, которое всегда равно единице. Изменение
раскладки заголовка - новая магия (`RBSNAP02`).

`stateLength` ограничен 1 ГиБ: больше - `Corrupt`, а не попытка выделить память. Граница
нормативная: снапшот состояния больше гигабайта означает, что сжатие не работает, и узнать
об этом надо на чтении, а не падением по памяти на следующем шаге.

## 5. Контрольные суммы

CRC-32C (Castagnoli), параметры и контрольные векторы - §5 `log-segment.md`; реализация
одна на всё хранилище (`Integrity/Crc32C.cs`).

- `headerCrc32C` считается по байтам `0..43` заголовка, то есть по всем полям, кроме самого поля CRC.
  Проверяется первым: без него остальные поля - это не числа, а мусор, и проверять по ним длину
  состояния бессмысленно.
- `stateCrc32C` считается по байтам состояния как они лежат в файле.

## 6. Правила чтения

Чтение идёт в этом порядке, и первое же нарушение - отказ (`InvalidDataException` с причиной),
а не «снапшота нет»:

1. Размер файла не меньше `HeaderSize` - иначе `Truncated`.
2. `magic` совпадает с `RBSNAP01` - иначе `Corrupt`.
3. `headerCrc32C` совпадает с CRC-32C байтов `0..43` - иначе `Corrupt`.
4. `lastIncludedIndex` больше нуля - иначе `Corrupt`.
5. `stateLength` не больше 1 ГиБ - иначе `Corrupt`.
6. Размер файла ровно `HeaderSize + stateLength` - иначе `Corrupt` (и короткий, и длинный файл).
7. `stateCrc32C` совпадает с CRC-32C байтов состояния - иначе `Corrupt`.

Проверка полного размера до чтения состояния - это то, что делает обрыв записи видимым:
усечённый файл отличается от целого длиной, и читать его целиком в память не нужно.

Файл, у которого нарушена любая проверка, не удаляется и не переписывается хранилищем: это
единственная копия состояния, и решение о ней принимает человек (та же логика, что у порчи
сегмента, §9.4 `log-segment.md`).

## 7. Публикация файла

Снапшот никогда не пишется по месту. Порядок шагов один и тот же на всех платформах:

1. Создать `snapshot-{index:D20}.snap.tmp` (семантика «только новый»).
2. Записать заголовок и состояние.
3. `fsync` файла.
4. Закрыть файл.
5. Переименовать `.tmp` в `snapshot-{index:D20}.snap` (замена запрещена: имя занято - ошибка).
6. `fsync` каталога, чтобы переименование пережило крах.

Промежуточных состояний, читаемых как валидный снапшот, не существует: до шага 5 в каталоге
лежит файл с суффиксом `.tmp`, который снапшотом не считается (§2), а после шага 5 файл уже
целый - он был сfsync-ан до переименования.

Крах между шагами 1 и 4 оставляет `.tmp`, который никто не читает; хранилище удаляет такие
файлы при следующем обращении к каталогу (они не несут состояния, которое кто-либо видел
опубликованным). Крах между шагами 5 и 6 оставляет либо старый набор снапшотов, либо новый;
это допустимо: оба валидны, а выбор «какой из них последний» решается по имени файла (§2),
а не по порядку появления в каталоге.

`fsync` каталога - единственный шаг, у которого нет переносимой формы: на POSIX это
`fsync` дескриптора каталога, на Windows дескриптор каталога открывается отдельным флагом
и `FlushFileBuffers` для него не определён. Реализация пытается сбросить каталог и,
если платформа этого не умеет, продолжает без него: сами метаданные каталога на NTFS
журналируются файловой системой. Это записано здесь, чтобы «сбой шага 6» не выглядел
одинаково на двух платформах (`docs/adr/0008-supported-platforms.md`, `0012`).

## 8. Несколько снапшотов в каталоге

- Актуальный - файл с наибольшим `lastIncludedIndex` (он же лексикографически последний по имени).
- Остальные - устаревшие; они удаляются ретеншном (`ISnapshotStore.DeleteOlderThanAsync`),
  когда журнал сжал следующую часть истории.
- Самый новый снапшот не удаляется никогда, даже если ретеншн просит индекс выше него:
  иначе узел остался бы без состояния, которое он уже отдал follower-ам.

## 9. Совместимость

- Изменение раскладки заголовка или смысла полей - новая магия (`RBSNAP02`), потому что
  магия здесь и есть версия (§4).
- Изменение формата байтов состояния - соглашение между приложением и его снапшотом, а не
  формата файла: хранилище состояние не толкует. Версия состояния - забота `StateMachine`
  и её собственного формата.
- Снапшот версии, которой узел не понимает, - отказ при старте, а не «нет снапшота»:
  иначе узел молча начал бы историю с нуля.

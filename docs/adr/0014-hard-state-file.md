# 0014. Файл hard state: append-only записи вместо двух слотов

* Статус: принято
* Дата: 2026-10-23
* Задача: `S2-T02`
* Формат: `docs/formats/hard-state.md`

## Контекст

Узлу нужно переживать рестарт два поля: `currentTerm` и `votedFor`. Их потеря ломает R6:
забывший голос узел голосует второй раз в том же term, и в кластере оказываются два лидера
в одном term. Запись обязана быть на устройстве **до** ответа на RPC.

К началу задачи в дереве есть:

* `IStorageFileSystem` с восемью операциями: `CreateAsync`, `OpenReadAsync`, `OpenAppendAsync`,
  `ListFilesAsync`, `TruncateAsync`, `DeleteAsync`, `RenameAsync`, `FlushDirectoryAsync`.
  Переименование **без замены** (`File.Move(..., overwrite: false)`): заменять существующий
  файл интерфейс не умеет, и снапшоты (`S1-T09`) на этом построены.
* `IStorageFile` умеет `WriteAsync` (только в конец), `TruncateAsync`, `FlushToDiskAsync`.
  Записи по смещению нет - ни `Seek`, ни `WriteAt`.
* `Crc32C`, `ILogStore` с сегментами и восстановлением обрыва (`S1-T07`).

Рассматривались три варианта.

**Два фиксированных слота** `[header][slot0][slot1]`: пишем слот с меньшим `sequence`, читаем
валидный с большим. Требует записи по смещению: слот 0 лежит в начале файла. Без `Seek`
единственный способ - усечь файл и переписать оба слота, но между усечением и `fsync` файл
содержит неполное состояние, и крах в этом окне уничтожает **оба** слота - ровно та потеря,
от которой слоты и защищают. Вариант непригоден на текущем интерфейсе.

**Временный файл + переименование с заменой** (как у снапшотов): новый файл, `fsync`,
переименование поверх старого. Замены в интерфейсе нет: `RenameAsync` падает, если приёмник
существует. Добавить замену - значит расширить примитив ради одного файла и потерять
инвариант «переименование не перетирает» у снапшотов, где он и есть защита.

**Append-only файл записей с CRC**: каждая запись самодостаточна, текущее состояние -
последняя целая. Работает на `OpenAppendAsync` + `FlushToDiskAsync` + `TruncateAsync`
без новых операций интерфейса.

## Решение

Файл `hard-state` - append-only последовательность записей: `magic`, `sequence`, `currentTerm`,
`votedForLength`, `votedFor`, CRC-32C. Одна запись на переход состояния. Чтение - сканирование
с начала, состояние берётся из последней целой записи.

Обрыв и порча различаются по признаку «помещается ли запись в файл целиком»:

* не хватает байтов до конца файла - обрыв, хвост усекается при открытии;
* целая по длине запись с плохим CRC (или сигнатурой, или `currentTerm < 0`) - порча,
  открытие падает с `InvalidDataException`.

Неудачная запись откатывается усечением до последней подтверждённой длины, а не повторным
сканированием: запись, на которой упал `fsync`, могла оказаться на диске целиком, но
подтверждённой не была.

## Обоснование

1. **Корректность на крахе.** Подтверждённая запись всегда сброшена на устройство, и она
   всегда последняя целая. Недописанная видна как обрыв (не помещается в файл) и усекается.
   Промежуточного состояния, которое читается как валидное, нет.
2. **Ноль новых операций интерфейса.** Требуется только то, что уже есть и покрыто тестами
   `S1`: append, `fsync`, усечение. Ни один существующий инвариант хранилища не ослаблен -
   в частности, «переименование не перетирает» остаётся в силе для снапшотов.
3. **Порча не откатывается к предыдущему term.** Откат означал бы забытый голос и второй голос
   в том же term. Правило «порча - стоп» то же, что у сегментов журнала (`S1-T04`).
4. **Один формат для всех платформ.** Нет ветвлений по ОС (ADR `0008`), нет `Seek`,
   нет зависимости от поведения `truncate` на Windows и Linux.

## Последствия

* Файл растёт: одна запись (30 байт + идентификатор) на новый term и на голос. Компакции нет.
* `votedForLength` - `uint16` (до 512 байт), а не `byte`: 128 символов идентификатора в UTF-8
  не помещаются в байт.
* Усечение при открытии - операция записи; если файловая система доступна только на чтение,
  открытие упадёт с ошибкой ввода-вывода, а не проигнорирует хвост молча.
* Второй файл рядом не появляется: начальное состояние - отсутствие файла, а не файл с нулями.
* `ReadAsync` кэширует состояние в памяти; после рестарта процесса источником истины остаётся
  файл.

## Чего решение не делает

* Не компактит файл: при тысячах term в сутки понадобится переписать последнюю запись в новый
  файл (для этого достаточно того же интерфейса, но это отдельная задача).
* Не заменяет снапшот и не хранит `commitIndex`.
* Не защищает от порчи самого устройства: CRC ловит обрыв и битовую порчу записи, но не
  подмену файла целиком. Это вне модели угроз R6 (там крах, а не злой администратор).
* Не даёт группового коммита: одна запись - один `fsync`, как и требует правило
  persist before respond.

# ADR 0004. Долговечность: групповой fsync по умолчанию, периодический режим без таймера внутри писателя

- **Дата:** 2026-09-30
- **Статус:** accepted
- **Задача:** `S1-T03` — `SegmentWriter`: append, буферизация, три политики fsync, rollover по размеру
- **Решает открытое решение этапа S1:** пункт 4 (как реализовать политику fsync и кому принадлежит интервал периодического режима)
- **Опирается на уже принятое решение владельца:** 2026-09-28 — режим по умолчанию `group commit`; и на выбор владельца в `S1-T03` — периодический режим реализуется явным flush, интервал принадлежит актору `S1-T08`
- **Опирается на ADR:** `0003-log-segment-format.md` (порядок rollover, размер сегмента), `0002-test-doubles-location.md` (дубли живут в `RaftBroker.TestKit`)

## Контекст

Запись в журнал Raft долговечна ровно тогда, когда байты пережили падение процесса и машины, то есть после `fsync`. Но `fsync` стоит миллисекунды и является самой дорогой операцией записи: он один определяет пропускную способность лидера. Отсюда три режима из эскиза этапа — `per entry` (fsync на запись), `group commit` (один fsync на группу записей) и `periodic` (fsync по расписанию, а не по записи).

Четыре вопроса нельзя решить молча, потому что каждый из них меняет либо интерфейс, либо тесты:

1. Какой режим использовать по умолчанию, если вызывающий его не назвал.
2. Где живёт интервал периодического режима: внутри писателя (свой таймер) или у того, кто его вызывает.
3. Как тест доказывает, что политика влияет на настоящие вызовы `fsync`, а не только на комментарий. Чек-лист ревью R1 требует именно наблюдения.
4. Откуда писатель берёт `createdAtUnixMs` для заголовка сегмента: `IClock.TimestampMs` монотонен (`Environment.TickCount64`, миллисекунды с загрузки), а формат требует Unix-миллисекунды.

## Решение

| Вопрос | Решение |
|---|---|
| Режим по умолчанию | `GroupCommit`: один `fsync` на вызов `AppendAsync` |
| `PerEntry` | `fsync` после каждой записи. Эталон для тестов долговечности; в продакшне не нужен |
| `Periodic` | `append` не вызывает `fsync` вовсе; долговечность даёт явный `FlushToDiskAsync` |
| Интервал `Periodic` | Принадлежит актору `S1-T08`, не писателю. Ориентир — порядка 10 мс, уточняется измерением в `S8-T05` |
| Таймер внутри `SegmentWriter` | Нет. Класс не создаёт потоков и не зависит от реального времени |
| `Periodic` в commit-пути Raft | Запрещён: подтверждение клиенту выдаётся только после `fsync` |
| Наблюдаемость `fsync` | Через `IStorageFile`/`IStorageFileSystem`: тестовый дубль считает вызовы и умеет падать на заданной операции |
| Конкурентность | Один писатель. `SegmentWriter` не потокобезопасен и не притворяется им; сериализация — задача `S1-T08` |
| Порядок rollover | `fsync` запечатываемого сегмента → создать и `fsync` заголовок нового → писать фрейм (ADR 0003, §8 формата) |
| `createdAtUnixMs` | Из нового поля `IClock.UnixTimeMs`; `TimestampMs` для этого не годится |

## Обоснование

### Групповой commit по умолчанию

- Цена `fsync` на порядки больше цены записи байтов, поэтому выигрыш даёт не «писать быстрее», а «реже синхронизировать». Записи, предложенные лидером одной пачкой, попадают в один `AppendAsync` и делят один `fsync` — это и есть групповой commit.
- Гарантии при этом не слабее: возврат из `AppendAsync` в любом режиме, кроме `Periodic`, означает, что данные на устройстве. `PerEntry` даёт ровно те же гарантии, но платит `fsync` за каждую запись, поэтому по умолчанию он не нужен.
- `Periodic` выбран не по умолчанию именно потому, что нарушает гарантию: возврат из `AppendAsync` перестаёт означать долговечность. Такой режим не может обслуживать commit-путь Raft, и он остаётся явным выбором вызывающего для записей, которые не подтверждаются клиенту.

### Периодический режим: таймер у актора, а не у писателя

- Таймер внутри писателя означал бы второй поток (или периодическую задачу) внутри низкоуровневого компонента, который пишет байты. Это делает `SegmentWriter` конкурентным объектом там, где конкурентность не нужна: у него и так ровно один вызывающий.
- Тесты политик стали бы зависеть от реального времени: «fsync не вызывался» проверялось бы ожиданием, а не наблюдением. Проект запрещает `Thread.Sleep` в тестах и требует виртуальное время — таймер внутри писателя этому прямо противоречит.
- Расписание уже есть у актора `S1-T08`: у него цикл обработки команд, и он же знает, когда заканчивается пачка. Интервал — его параметр, а не свойство формата; изменение интервала не должно требовать правки хранилища.
- Граница проходит по вопросу «кто принимает решение о времени». Писатель принимает решение о позиции байтов (rollover по размеру), актор — о времени (`fsync` по расписанию). Это разделение и записано тестом: `Rollover` в режиме `Periodic` всё равно вызывает `fsync` запечатываемого сегмента, потому что обязательный порядок §8 не является периодической политикой.

### Наблюдаемость вместо обещаний: `IStorageFile`/`IStorageFileSystem`

- Проверить, что режим влияет на `fsync`, через `FileStream` нельзя: число вызовов `Flush(true)` снаружи не видно, а мокать `FileStream` — значит тестировать мок, а не поведение.
- Отсюда узкий шов из двух интерфейсов: файл (дозапись + `fsync` + закрытие) и фабрика файлов (создание «только нового»). Он даёт тестам счётчик `fsync`, журнал операций (для проверки порядка §8) и инъекцию отказа в заданной точке — последнее понадобится crash-тестам `S1-T05` и `S1-T09`, где падение процесса моделируется реальным завершением, а не только моком.
- Реализация по умолчанию (`SystemStorageFileSystem`) пишет через `FileStream` с `FileOptions.Asynchronous` и делает `fsync` через `Flush(flushToDisk: true)`. Асинхронный `fsync` в .NET не существует; оборачивать синхронный вызов в `Task.Run` значило бы прятать реальную цену операции от планировщика и от бенчмарков `S8-T05`.
- Создание файла имеет семантику «только новый» (`FileMode.CreateNew`): формат запрещает перезапись сегмента, поэтому потеря существующего файла обязана быть видна как ошибка, а не как тихая замена данных.

### Один писатель

- Формат append-only и не предполагает конкурентной записи одного файла. Любая блокировка внутри `SegmentWriter` была бы лишней: узел Raft применяет команды в одной точке, и эта точка — актор `S1-T08`.
- Порядок проверок тоже часть контракта: неверная последовательность индексов или убывающий терм обнаруживаются **до** первого байта на диске, чтобы отказ не оставлял журнал наполовину записанным.

### Настенное время в `IClock`

- Формат называет поле `createdAtUnixMs` и описывает его как Unix-миллисекунды (§3). `SystemClock.TimestampMs` — это `Environment.TickCount64`, то есть миллисекунды с загрузки; запись его в это поле нарушала бы нормативный документ, хотя поле и информационное.
- В проекте уже есть единый шов времени — `IClock`, и второй источник времени рядом с ним означал бы, что «время в системе» берётся из двух разных мест. Поэтому `IClock` получил второе поле: `UnixTimeMs` — настенное время Unix, отдельно от монотонного `TimestampMs`.
- Разделение не косметическое: монотонное время нужно таймаутам (перевод часов назад не должен ломать выборы), настенное — информационным меткам (их читает человек и они должны совпадать с календарём). `TestClock` хранит оба значения независимо, чтобы тест не мог случайно подменить одно другим.

## Последствия

- `IClock` расширен аддитивно (`UnixTimeMs`); `SystemClock` берёт `DateTimeOffset.UtcNow`, `TestClock` — из конструктора или `SetUnixTimeMs`. Правка не меняет ни одного существующего поведения: S0-T04 остаётся закрытым, а его тезис «время подменяемо» только усиливается.
- `S1-T08` обязан: владеть интервалом `Periodic`, вызывать `FlushToDiskAsync` по расписанию, не применять `Periodic` в commit-пути и сериализовать всех писателей через один актор.
- `S1-T05`/`S1-T09` используют `FailureInjector` дубля для отказа на конкретной операции и реальное завершение процесса для проверки восстановления.
- Границы слоёв: чтобы `RaftBroker.TestKit` мог реализовать `IStorageFileSystem`, тестовый проект теперь ссылается на `RaftBroker.Storage`, а его ранг в `LayerReferenceTests` поднят с 1 до 99 (выше всех боевых слоёв, ниже тестовых проектов). Это осознанная правка таблицы слоёв, а не ослабление теста: боевые проекты по-прежнему не могут ссылаться на тестовые.
- Читающая сторона (`S1-T04`/`S1-T05`) решением не затронута: формат не изменился, сегмент любого размера принимается как раньше.
- Значение интервала (ориентир 10 мс) — предмет измерения `S8-T05`/`S8-T06`, а не часть формата: его изменение не требует новой версии и не меняет байты на диске.
- Буферизация остаётся за `FileStream` (буфер 4 КиБ): политика решает, когда буфер процесса и буфер ядра уходят на устройство, но не подменяет собой буферизацию записи. Свой буфер писателя в версии 1 не вводится — сначала корректность, потом измерения (та же логика, что у отказа от файла индекса в ADR 0003).

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Таймер `Periodic` внутри `SegmentWriter` | Делает низкоуровневый писатель конкурентным и зависимым от реального времени; тесты политики перестают быть детерминированными; расписание уже есть у актора `S1-T08` |
| `PerEntry` по умолчанию | Те же гарантии, что у `GroupCommit`, но `fsync` на каждую запись: пропускная способность падает без выигрыша в корректности |
| `Periodic` по умолчанию | Возврат из `AppendAsync` перестал бы означать долговечность; commit-путь Raft не может на это опираться |
| Писать `IClock.TimestampMs` (`TickCount64`) в `createdAtUnixMs` | Противоречит нормативному §3 формата; поле перестало бы совпадать с календарём, а диагностическая ценность — с ней |
| Отдельный источник Unix-времени в `Storage` рядом с `IClock` | Два источника времени в проекте; рано или поздно один из них начнут использовать там, где нужен другой |
| Мокать `FileStream` в тестах | Тест проверял бы настройку мока, а не то, что режим действительно меняет число `fsync`; инъекция отказа в нужной точке записи стала бы невозможной |
| Асинхронная обёртка над `FileStream.Flush(true)` | Прячет синхронную цену `fsync` от планировщика и бенчмарков; собственный буфер ради этого усложняет писатель без измеренной выгоды |
| Свой буфер записи вместо буфера `FileStream` | Преждевременная оптимизация: выгода не измерена, а корректность политик уже обеспечена швом `IStorageFile` |
| Блокировка (`SemaphoreSlim`) внутри `SegmentWriter` | Защищала бы от ошибки, которой при контракте «один писатель» быть не должно, и скрывала бы её; сериализация — ответственность актора `S1-T08` |

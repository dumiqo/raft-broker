# 0017. Переходы роли и терма - в одной функции и одном методе

* Статус: принято
* Дата: 2026-10-23
* Задача: `S2-T08`
* Спецификация: `docs/stages/02 - Raft roles and elections.md`

## Контекст

К концу S2 решение «уходить в follower или нет» повторялось в шести местах: `RequestVote`,
`PreVote`, `AppendEntries`, ответы на свой запрос голосов, ответы на heartbeat, таймаут. Копии
уже разошлись: `RequestVote` сбрасывал таймер, а `AppendEntries` - нет; рост терма по чужому
запросу голоса не очищал репликаторы лидера. Каждая новая роль или сообщение добавляли седьмую
копию.

## Решение

### 1. Разбор терма - одна чистая функция

```csharp
internal static class RaftRoleTransitions
{
    public static StepKind Decide(Term currentTerm, Term incomingTerm);
}

internal enum StepKind { Ignore, StepDown, ProcessInTerm }
```

Три исхода на все сообщения: меньше - игнор, больше - уход, равен - обычная обработка по роли.
Роль в разборе **не участвует**: переход по терму от неё не зависит, а нужна она дальше -
обработчику, который знает, что делать с сообщением своего терма.

### 2. Смена роли - один метод

`RaftNode.StepDownAsync(newTerm)` - единственное место, где меняются `Role`, `CurrentTerm`,
`VotedFor`, `LeaderId` и умирают ролевые ресурсы (репликаторы, таймер выборов):

```
если newTerm > currentTerm: PersistAsync(newTerm, votedFor: null)   // диск только при росте
Role = Follower; LeaderId = null; LeaveRole()
```

Уборка ресурсов вынесена в `LeaveRole` и вызывается ещё в одном месте - после `RequestVoteHandler`,
который меняет терм и голос сам. Причина в §3.

## Отклонение от формы задачи

Тело задачи предлагало `StepKind { Ignore, StepDown, BecomeCandidate, BecomeLeader }`. Взято три
значения, потому что победа и таймаут - **не** переходы по терму входящего сообщения, а события
узла. Смешав их в функции `Decide(role, current, incoming)`, пришлось бы отвечать на вопрос
«что делать, если пришёл терм больше, а узел победил», которого в жизни не бывает, и проверять
в матрице ячейки, которых нет. Победа (`BecomeLeaderAsync`) и участие в выборах
(`BeginVoteRoundAsync`) остались отдельными методами: у них нет входящего терма.

## Обоснование

**Почему диск пишется только при росте терма.** Смена роли без роста терма не делает ничего
долговечным: после рестарта узел всё равно начнёт follower'ом (§5.1). Зато лишняя запись на
каждом heartbeat, который переводит кандидата в follower, - это fsync на ровном месте. Рост
терма, наоборот, обязан быть долговечным: иначе узел, проголосовавший в терме 5, после краха
вернётся в терм 4 и проголосует второй раз в том же терме.

**Почему `VotedFor` не сбрасывается при смене роли внутри терма.** Правило §5.2 запрещает два
голоса в одном терме. `Candidate → Follower` по heartbeat своего терма означает, что лидер этого
терма существует, но голос уже отдан - и это единственное, что защищает от второго голоса.

**Почему `StepDownAsync` идемпотентен.** Повторные сообщения с одним и тем же термом нормальны
(ретраи транспорта, дубли heartbeat). Второй вызов не должен ни писать на диск, ни менять голос:
тест `StepDown_IsIdempotentAndWritesOnce` считает записи.

**Почему `RequestVote` не ходит через `StepDownAsync`.** Голос и терм обязаны лечь **одной**
записью: узел, записавший терм без голоса, после краха выглядел бы как «в этом терме ещё можно
голосовать». `RequestVoteHandler` пишет обе величины одной операцией, а уборку ролевых ресурсов
узел делает после него через `LeaveRole`.

## Последствия

* Матрица 3 роли × 3 знака живёт в тесте как данные (`RaftRoleTransitionTests.Matrix`), а не
  девятью методами: новая ветка добавляется строкой таблицы.
* Обработчики перестали сравнивать термы вручную; сравнение в коде осталось только в
  `RaftRoleTransitions` и в `RequestVoteRules` (там оно часть правила голосования).
* `LeaderId` - подсказка, корректность на ней не строится: `StepDown` обнуляет её, а
  `AppendEntries` сразу заполняет заново.

## Чего решение не делает

* Не переносит матрицу в спецификацию этапа: это откроется при ревью `R2`.
* Не решает, что делать с равным термом при живом втором лидере: сейчас узел уходит в follower,
  и это безопаснее, чем два лидера в одном терме.
* Не отменяет in-flight RPC: на S2 отправки синхронные и ни одна не переживает `StepDown`.
  Настоящие отмены появятся вместе с настоящим транспортом (`S4-T01`).

# ADR 0006. Восстановление сегмента: усечение на месте, удаление недописанного, краш-тест отдельным процессом

- **Дата:** 2026-09-30
- **Статус:** accepted
- **Задача:** `S1-T05` — восстановление: обнаружение оборванной записи, усечение до последней валидной, отказ при порче в середине, случаи §9.3
- **Опирается на ADR:** `0003-log-segment-format.md` (порядок проверок §9.1, признаки оборванной записи §9.2, оборванное создание §9.3, запрет на усечение порчи §9.4, шаги §9.5, остаточный риск §9.6), `0004-durability-policies.md` (режимы `fsync`, шов `IStorageFileSystem`), `0005-log-reading.md` (`SegmentScanResult`, `ValidEndOffset`, примитивы проб)

## Контекст

Восстановление — первый код, который меняет файлы журнала. Читатель (`S1-T04`) намеренно не выносил вердикт: он сообщал `TailProblem` и `ValidEndOffset`, потому что по одному файлу нельзя отличить «оборванный хвост последнего сегмента» (§9.3, усечь) от «порчи» (§9.4, отказ). Теперь это различие нужно провести, и от него зависят вопросы, ответы на которые меняют и формат работы с диском, и API:

1. Кто решает судьбу сегмента и откуда берётся знание «последний он или запечатанный».
2. Как усекать: перезаписью файла целиком, копией во временный файл с переименованием или усечением на месте.
3. Что делать с файлом короче заголовка (§9.3 разрешает и удалить, и проигнорировать).
4. Кому принадлежит проба продолжения §9.5 шаг 5 — читателю как примитив или восстановлению как решение; и что именно она проверяет.
5. Что делать после усечения: пересканировать файл или довериться уже пройденному проходу.
6. Как проверять главное требование §9.6 — что усечение работает при настоящем завершении процесса, а не только на дубле файловой системы.

## Решение

| Вопрос | Решение |
|---|---|
| Владелец решения | `SegmentRecovery`: восстановление само решает и само действует (усекает, удаляет, отказывается). Читатель остаётся примитивом |
| Вид сегмента | Вход восстановления: `SegmentKind { Sealed, Last }`. Один файл не может ответить на этот вопрос, а знание есть у каталога (`S1-T07`) |
| Усечение | На месте: `TruncateAsync(path, length)` — только уменьшение, с `fsync` метаданных. Перезапись или копия с переименованием не делаются (§7 запрещает переименование) |
| Файл короче заголовка в последнем сегменте | Удаление (`DeleteAsync`), а не игнорирование: файл не может стать валидным никогда |
| Файл короче заголовка в запечатанном сегменте | Отказ: запечатанный сегмент не мог быть создан недописанным (§8) |
| Заголовок последнего сегмента не читается | Отказ, файл остаётся нетронутым (§9.3: «отказ от старта, а не удаление») |
| Порча в середине или в запечатанном сегменте | Отказ, диск не трогается ни одной разрушающей операцией (§9.4) |
| Проба продолжения | Собственность восстановления, но выполняется примитивами читателя; проверяется **структурно**: на `p + 4 + L + 4` лежит целый фрейм с верным CRC |
| Непрерывность индексов в пробе | Не проверяется: иначе настоящая порча превратилась бы в усечение, то есть в молчаливую потерю данных (§9.6) |
| После усечения | Повторного сканирования нет: префикс проверен тем же проходом, который нашёл хвост. Тесты и краш-тест проверяют, что файл после усечения сканируется как целый |
| Порядок операций | Читатель закрывается до `TruncateAsync`; разрушающих операций при отказе не бывает вообще (проверяется по журналу операций дубля) |
| Отказ | Значение результата `SegmentRecoveryStatus.Refused`, не исключение. Исключения остаются для ошибок вызывающего (нет файла, отмена) |
| Шов ввода-вывода | `TruncateAsync` (только уменьшение; `FileNotFoundException`, если файла нет) и `DeleteAsync` (отсутствие файла — не ошибка: повторный старт после падения между решением и удалением) |
| Реальная проверка | Отдельный проект-жертва `RaftBroker.CrashHarness` (14-й проект решения, ранг 98) и тест, который убивает процесс: `Process.Kill(entireProcessTree: true)` |

## Обоснование

### Решение и действие — в одном месте, вид сегмента — вход

- §9.3 и §9.4 различаются только одним: последний сегмент или нет. Читатель одного файла этого не знает, поэтому знание передаётся входом (`SegmentKind`), а не выводится из догадок. Перечислять каталог здесь было бы преждевременно: обход сегментов, проверка порядка и агрегация отчёта — задача `S1-T07`, и дублировать её в восстановлении значит получить две версии одного правила.
- Восстановление сразу выполняет действие, а не возвращает «приговор к исполнению»: единственный потребитель — старт узла, и разделение на «решить» и «применить» добавило бы состояние, которое некому хранить. Результат (`Status`, `Reason`, `ValidEndOffset`, `DroppedBytes`, число фреймов, последние индекс и терм) при этом остаётся данными: отчёт о восстановлении собирает `S1-T07`.
- Отказ — это значение, а не исключение, по той же причине, что в ADR 0005: испорченный журнал — ожидаемое состояние старта после падения, и превращать его в поток `try/catch` у вызывающего нельзя. Исключение означает ошибку в коде: файла нет вовсе, отмена запрошена, аргументы бессмысленны.

### Усечение на месте

- §9.2 требует именно физического усечения: обрезать файл, чтобы следующие старты видели целый сегмент, а не «хвост, который каждый раз надо толковать заново».
- Копия во временный файл с переименованием была бы единственной альтернативой, дающей ту же атомарность, что и запись: если процесс умрёт посреди копирования, старый файл остаётся цел. Но §7 запрещает переименование сегментов (имя — это `baseIndex`, и оно не меняется), а копирование требует места под второй файл рядом с 64-МиБ сегментом и превращает восстановление из «одного `SetLength`» в «полное чтение и полную запись».
- Надёжность усечения на месте держится на двух вещах: `SetLength` сам по себе атомарен для метаданных, а `fsync` метаданных гарантирует, что новую длину видно после краха. Если процесс умрёт до `fsync`, на диске останется прежний (оборванный) файл, и следующий старт повторит то же самое решение — идемпотентность здесь обязательна, и она проверена тестом на реальном диске.
- Усечение разрешено только «вниз»: попытка удлинить файл означала бы запись нулей в середину журнала, то есть выдумывание байтов, которых не было. Поэтому `TruncateAsync` падает на `length > текущей длины`, а не молча расширяет.
- Читатель закрывается до усечения намеренно: открытый на чтение дескриптор — это ещё одно окно, в котором файл выглядит иначе, чем на диске, и Windows-блокировка удаления. Порядок зафиксирован кодом, а не комментарием.

### Недописанный сегмент — удалять, а не игнорировать

- Файл короче 30 байт заголовка не может стать валидным сегментом никогда: имя даёт `baseIndex`, заголовок пишется и fsync-ается до первого фрейма (§8), а «дописать» его восстановление не вправе — оно не знает, что там должно было быть. Игнорирование оставляет в каталоге мусор, который `S1-T07` обязан вечно пропускать, и превращает каждый старт в разбор одного и того же случая.
- Удаление здесь безопасно именно потому, что записей в файле нет по построению: заголовок не дописан, значит не дописан и ни один фрейм. Инвариант R6 (подтверждённое переживает крах) при этом не нарушается: подтверждать такую запись было нечего.
- Для запечатанного сегмента то же состояние — отказ. Запечатанный сегмент уже был полным и fsync-нутым (§8), поэтому короткий файл здесь означает не оборванное создание, а потерю данных, и §9.4 предписывает остановиться.
- Заголовок последнего сегмента, который читается как мусор, — обратный случай: данные за смещением 30 могли уцелеть, поэтому §9.3 запрещает удаление и требует отказа. Восстановление не пытается «спасти префикс», пропустив заголовок: без заголовка неизвестны ни база, ни версия формата.

### Проба продолжения: структурная проверка, принадлежащая восстановлению

- §9.5 шаг 5 отвечает на вопрос «данные перестали сходиться в точке `p` — это оборванный хвост или порча?». Признак: если на `p + 4 + L + 4` (сразу за фреймом, который не удалось принять) лежит целый фрейм с верным CRC, значит за повреждением есть продолжение, и это порча. Если продолжения нет — это хвост, и его можно отбросить.
- Проверка оставлена структурной: `ReadFrameLengthAsync(p)` и `ReadFrameAtAsync(p + 4 + L + 4)`, без проверки непрерывности индексов и без сравнения термов. Соблазн усилить её отвергнут по §9.6: более строгая проверка превращает настоящую порчу (например, испорченный индекс в последнем фрейме при целых предыдущих) в усечение, то есть в тихую потерю подтверждённых данных. Ложный отказ стоит недоступности узла и разбора человеком; ложное усечение стоит данных. Выбор сделан в пользу отказа.
- Примитивы остаются у читателя (ADR 0005), потому что это операции над байтами сегмента, и у него уже есть корректная адресация по смещению. Восстановление владеет **решением**, а не разбором байтов.
- Смещение `p + 4 + L + 4` — то место, где закончился бы фрейм с длиной `L`: `4` байта длины + `L` байт тела + `4` байта CRC. Проба читает именно там, а не по индексу, потому что индекс после повреждения доверия не заслуживает.

### Проверка на живом процессе, а не на дубле

- §9.6 прямо называет остаточный риск: модель «байты в дубле» не воспроизводит поведение устройства при потере питания. Критерий выхода этапа сформулирован так: набор оборванных записей должен проходить на **настоящем** завершении процесса.
- Поэтому появился отдельный исполняемый проект-жертва: он пишет подтверждённые записи с `fsync` после каждой, дописывает оборванный фрейм (тоже с `fsync`, чтобы состояние после смерти было детерминированным), печатает `READY` и ждёт. Родительский тест убивает процесс (`TerminateProcess`/`SIGKILL`), то есть у жертвы нет ни одного шанса что-то сбросить или убрать за собой, и только потом запускает восстановление.
- Жертва не использует `SegmentWriter`: оборванный фрейм он записать не может по построению, а его `FileShare.Read` не даёт открыть второй дескриптор на запись. Байты собираются теми же кодеками (`SegmentHeaderCodec`, `LogFrameCodec`), что и у писателя, а порядок `fsync` повторяет `DurabilityMode.PerEntry`. Это осознанный компромисс: краш-тест проверяет формат и восстановление, а не то, что `SegmentWriter` вызывает `FlushToDiskAsync` (это проверяют тесты счётчиков в `S1-T03`).
- Отдельный проект, а не «жертва внутри тестовой сборки»: убивать надо другой процесс, а не тот, в котором работает тестовый раннер. Проект стоит в таблице слоёв на ранге 98 — ниже тестовых проектов (100), чтобы `IntegrationTests` мог на него ссылаться, и выше всех боевых слоёв, чтобы боевой код не мог случайно получить зависимость от тестовой сборки.
- Добавление 14-го проекта — решение об архитектуре, поэтому оно записано и в таблице слоёв (`LayerReferenceTests`, число проектов 13 → 14), и в разделе 3 плана, и здесь. Тест таблицы падает, если проект появится молча.

## Последствия

- `S1-T07` получает восстановление одного сегмента как операцию с одним входом `SegmentKind` и одним результатом: перечисление сегментов, проверка непрерывности базовых индексов и агрегация отчёта остаются его работой. Порядок обхода (от старого к новому, последний сегмент — последним) и решение «усекли последний — что делать с запечатанными» тоже его.
- Шов `IStorageFileSystem` расширен двумя операциями (`TruncateAsync`, `DeleteAsync`), а `SegmentOpenResult` — длиной файла на момент открытия: она нужна, чтобы отчёт об удалении знал, сколько байт пропало, не открывая исчезнувший файл заново.
- Восстановление не пересканирует файл после усечения. Если когда-нибудь понадобится отчёт «что именно осталось», его возьмут из того же результата: `ValidEndOffset`, `FrameCount`, `LastIndex`, `LastTerm`.
- Пустой сегмент (только заголовок) считается целым в обоих видах: нарушать формат восстановление не имеет права, а пустой файл с валидным заголовком формату не противоречит. Пустой запечатанный сегмент означает, что узел запечатал сегмент, ничего в него не записав, — это вопрос к `S1-T07`, а не к восстановлению.
- Тексты причин отказа — часть наблюдаемого поведения: они попадают в отчёт о старте, и тесты проверяют в них ссылки на §9.1, §9.3, §9.4 и §9.5 шаг 5. Менять их формулировки можно, но ссылка на раздел формата должна остаться.
- Краш-тест занимает процесс целиком и потому не может проверять все точки обрыва: он проверяет две (оборванный фрейм, оборванный заголовок). Полный перебор точек — работа тестов на дубле, и эти два уровня проверки не заменяют друг друга.
- Тест `LayerReferenceTests.LayerTable_ListsExactlyTheProjectsThatExist` теперь требует 14 проектов: следующий новый проект обязан пройти ту же процедуру (таблица слоёв, план, ADR).

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Решение о судьбе сегмента в читателе | Читатель одного файла не знает, последний он или запечатанный; вердикт требовал бы догадки по тексту причины |
| Восстановление возвращает «приговор», а применяет кто-то другой | Единственный потребитель — старт узла; разделение добавило бы состояние, которое некому хранить |
| Копия в временный файл с переименованием | §7 запрещает переименование сегментов; копия 64-МиБ сегмента ради усечения хвоста |
| Перезапись файла целиком на месте | Требует чтения и полной записи, а крах в середине перезаписи теряет уже проверенный префикс |
| Усечение без `fsync` метаданных | Новая длина не гарантирована после краха: следующий старт увидит прежний оборванный файл, и «успешное восстановление» окажется мнимым |
| `TruncateAsync` с расширением файла | Удлинение дописало бы нули в середину журнала, то есть выдумало байты |
| Игнорировать файл короче заголовка | Мусор в каталоге, который `S1-T07` обязан вечно пропускать; файл не станет валидным никогда |
| Дописать заголовок короткому файлу | Восстановление не знает, что там должно было быть; база и версия формата берутся из заголовка, а не из догадки |
| Отказ при нечитаемом заголовке последнего сегмента считать удалением | §9.3 требует обратного: за смещением 30 могли уцелеть данные |
| Проба продолжения с проверкой непрерывности индексов | Настоящая порча превратилась бы в усечение — молчаливая потеря подтверждённых данных (§9.6) |
| Проба продолжения «на глазок»: непустой файл за повреждением | Остаток может быть мусором от той же порчи; признак §9.5 — целый фрейм с верным CRC |
| Пересканировать файл после усечения | Повторный проход по префиксу, который уже проверен тем же кодом; результат сканирования и так есть в отчёте |
| Восстановление как метод писателя или читателя | Это третья роль: писатель только добавляет, читатель только читает, восстановление — единственный, кто меняет существующий файл |
| Жертва краха внутри тестовой сборки | Убивать надо другой процесс; сборка тестов не может убить саму себя |
| Краш-тест на `SegmentWriter` | Оборванный фрейм писателем не получить по построению; проверяется формат, а не вызовы `fsync` |

# ADR 0002. Тестовые дубли живут в tests/RaftBroker.TestKit, а не в RaftBroker.Core

- **Дата:** 2026-09-29
- **Статус:** accepted
- **Задача:** S0-T04 (перенос - follow-up к S0-T04, сделан до S0-T05)
- **Повод:** ревью владельца: "почему TestClock находится в RaftBroker.Core, кажется что всё, что связано с тестами, должно быть в папке tests"

## Контекст

S0-T04 вводит `TestClock` - виртуальное время для тестов. Ему нужны все три тестовых проекта и будущий детерминированный симулятор S8-T01, а общей библиотеки для тестов в структуре решения нет: в плане ровно четыре проекта в `tests/`, и ни один из них не является переиспользуемой библиотекой.

Первая версия положила `TestClock` в `RaftBroker.Core/Testing/`, потому что `Core` ссылают все тестовые проекты. Ревью это отклонило по существу:

- тестовый дубль уезжает в боевую сборку `RaftBroker.Core.dll`;
- `AdvanceTo`, `PendingTimerCount` и прочие приёмы тестирования становятся публичным API продукта;
- вопрос "почему боевая библиотека везёт тестовые часы" не имеет ответа, кроме "не хотелось добавлять проект".

## Решение

Появился тринадцатый проект `tests/RaftBroker.TestKit`:

- обычная библиотека (`Microsoft.NET.Sdk`, без `OutputType=Exe`);
- **никаких пакетов тест-фреймворков и библиотек ассертов**: только ссылка на `RaftBroker.Core`. Так его сможет использовать и `Benchmarks`, и будущий нагрузочный стенд, которым xunit не нужен;
- ссылается из `RaftBroker.UnitTests`, `RaftBroker.IntegrationTests`, `RaftBroker.SimulationTests` (у `Benchmarks` ссылка появится, когда в нём возникнет нужда в фейках);
- здесь же будут жить будущие дубли: ненадёжное хранилище (S1), управляемый транспорт (S4), детерминированные сборщики историй (S8).

`src/RaftBroker.Core` оставляет за собой только боевые реализации: `IClock`/`ITimer`/`SystemClock` и `IRandomSource`/`SystemRandomSource`/`SeededRandomSource`.

Пространства имён повторяют папки: `RaftBroker.TestKit.Time` (файл `Time/TestClock.cs`). Внутри `TestClock` типы ядра подключаются алиасами `CoreClock`/`CoreTimer`, иначе `ITimer` конфликтует с `System.Threading.ITimer`, появившимся в .NET 8, при импортированном `RaftBroker.Core.Time`.

## Последствия

- Число проектов в решении **12 → 13**, из них 8 боевых и 5 в `tests/` (три тестовых, `Benchmarks`, `TestKit`). Это правится в плане и в спецификации этапа S0: иначе через неделю кто-то сверит DoD с фактом и решит, что появился лишний проект.
- `dotnet test` по-прежнему запускает три проекта: `TestKit` - библиотека, `Benchmarks` - консольное приложение с `Main`, который конфликтует с точкой входа xunit.v3.
- Помощники для ассертов (`AwesomeAssertions`) и генераторы `FsCheck` в `TestKit` не переезжают: дубли должны оставаться свободными от тест-фреймворков (решение владельца). Если понадобится общий код ассертов, он появится отдельным проектом `tests/RaftBroker.TestAssertions`, а не размыванием границы этого.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Оставить `TestClock` в `RaftBroker.Core/Testing/` | Тестовый код и его публичный API в боевой сборке |
| Папка `tests/Shared/` с `<Compile Include="...">` в каждом тестовом проекте | Число проектов не меняется, но каждый тестовый проект компилирует свою копию типов, а пакеты, нужные общему коду, приходится дублировать во всех csproj; для .NET-решения это нестандартно |
| Дубли в каждом тестовом проекте отдельно | Три копии часов разъедутся, а детерминизм S8 требует ровно одних |
| Ссылка `UnitTests` на тестовый проект `SimulationTests` | Тестовый проект-приложение как библиотека: хрупко и бессмысленно |

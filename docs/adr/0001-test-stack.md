# ADR 0001. Тестовый стек: xunit.v3, AwesomeAssertions, FsCheck

- **Дата:** 2026-09-29
- **Статус:** accepted
- **Задача:** S0-T03 - "Тестовые проекты, базовые хелперы; выбор библиотеки ассертов зафиксирован" (план работ живёт в Obsidian, не в этом репозитории)
- **Решает открытые вопросы этапа S0** из `stages/00 - Foundations.md` (пункты 1 и 2) и версию xUnit, которую план оставлял открытой ("xUnit" без мажора)

## Контекст

План фиксирует только "xUnit, NSubstitute, coverlet; библиотека ассертов выбирается в S0-T03". Property-based тесты нужны в S1-T02 (формат сегмента), S2 (выборы) и S5-T10 (детерминизм редьюсера), поэтому движок выбирается здесь же, а не "потом".

Тестовый стек - та часть решения, которую нельзя поменять дёшево: от него зависит синтаксис всех последующих тестов, поэтому решение фиксируется ADR, а не правкой csproj по ходу дела.

## Решение

| Компонент | Выбор | Версия |
|---|---|---|
| Фреймворк тестов | `xunit.v3` | 4.0.1 |
| Библиотека ассертов | `AwesomeAssertions` | 9.6.0 |
| Property-based движок | `FsCheck` + собственные генераторы домена | 3.4.0 |
| Запуск | `Microsoft.Testing.Platform` (opt-in через `global.json`) | - |

Тестовый проект xunit.v3 - это исполняемая сборка (`<OutputType>Exe</OutputType>`); `Microsoft.NET.Test.Sdk` и `xunit.runner.visualstudio` **не подключаются**.

## Обоснование: проверенные факты

Всё ниже проверено распаковкой `.nuspec` из nuget.org и запуском, а не пересказом обзоров.

1. **AwesomeAssertions вместо FluentAssertions.** У `FluentAssertions` 8.11.0 поле `license` содержит `LICENSE` (то есть свою лицензию), а `projectUrl` ведёт на `xceed.com/products/unit-testing/fluent-assertions/` - с версии 8.0 это платная лицензия Xceed для коммерческого использования. `AwesomeAssertions` 9.6.0 - форк той же кодовой базы под Apache-2.0, синтаксис FluentAssertions сохранён, и в пакете есть сборка под `net8.0` (у FluentAssertions 8.11.0 её нет: только `netstandard2.0` и `net6.0`).
2. **Shouldly 4.3.0 отклонён владельцем** (BSD-3-Clause, `net8.0` есть, лицензия чище всех) - выбран вариант с более богатым API для сравнения коллекций и графов объектов, потому что тесты состояния очереди (S5) проверяют структуры, а не отдельные значения.
3. **xunit.v3 4.0.1.** Apache-2.0, есть сборка под `net8.0`. Замена на v2 позже была бы миграцией тестов, а не сменой пакета.
4. **VSTest на SDK 10 не работает с xunit.v3.** Пробный проект упал с текстом: `Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later. If you use dotnet test, you should opt-in to the new dotnet test experience.` Opt-in делается файлом `global.json` (`{"test": {"runner": "Microsoft.Testing.Platform"}}`); после этого пробный тест прошёл. Свойство `TestingPlatformDotnetTestSupport` само по себе проблему не решает.
5. **FsCheck 3.4.0** - BSD-3-Clause, `netstandard2.0` (работает на `net8.0`). Берётся как движок ради shrinking: падающий property-тест сам уменьшает контрпример до минимального. Доменные генераторы (`Arbitrary` для термов, логов, историй) пишутся свои, потому что встроенные генераторы дают мусорные истории, которые домен отвергает по валидации.

## Последствия

- `dotnet test` для решения требует явного флага: `dotnet test --solution RaftBroker.sln`. Форма `dotnet test RaftBroker.sln` отвечает `Specifying a solution for 'dotnet test' should be via '--solution'`. Это учитывается в `scripts/verify.ps1` и в CI (S0-T08).
- **CI обязан собирать на SDK 10 и иметь рантайм .NET 8**: SDK 10 нужен для нового `dotnet test`, рантайм 8.0 - чтобы запускать тесты, собранные под `net8.0`.
- Тестовые проекты - приложения, а не библиотеки. Это ломает привычку "тестовый проект нельзя запустить вручную из консоли": теперь можно, и это удобно для диагностики.
- `global.json` фиксирует SDK (`10.0.100`, `rollForward: latestFeature`). Машина с одним SDK 8 не соберёт решение - это осознанное ограничение, а не поломка: TFM решения `net8.0`, но инструменты сборки и тестов - SDK 10.
- `NSubstitute` и `coverlet` остаются из плана, но подключаются, когда появятся первые моки и первый прогон покрытия (S1+). Пока их версии в `Directory.Packages.props` не пришпилены: правило S0-T02 - версия приходит с той задачей, которая её проверяет сборкой.
- `FsCheck` подключается на S1-T02 (первый настоящий property-тест), а не на S0-T03: на S0-T03 в `Core` ещё нет типов, свойства которых можно проверять.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| `FluentAssertions` 8.x | Проприетарная лицензия Xceed в зависимости проекта, которая попадёт в README и в вопросы на интервью |
| `Shouldly` | Лицензия лучше, но API для сравнения структур беднее; отклонён владельцем |
| `xunit` 2.9.3 (линия v2, её же генерирует шаблон SDK 10) | Обкатана, но линия в режиме поддержки; миграцию всё равно придётся делать |
| Свой генератор вместо `FsCheck` | Нет shrinking: падающий тест сообщает большой случайный вход, и поиск бага становится ручным |
| Только `FsCheck` без своих генераторов | Свойства вырождаются в проверку валидатора на мусорных входах |
| `TestingPlatformDotnetTestSupport=true` | Проверено: нужный opt-in делается только через `global.json`, это свойство проблему не решает |

# ADR 0012. Файл снапшота и атомарная публикация: rename плюс сброс каталога

- **Дата:** 2026-10-23
- **Статус:** accepted
- **Задача:** `S1-T09` — формат файла снапшота и запись, которая либо доводит файл до целого, либо не оставляет его вовсе
- **Опирается на ADR:** `0003-log-segment-format.md` (соглашения формата: little-endian, CRC-32C, имена фиксированной длины), `0006-log-recovery.md` (отказ как значение, «мусор остаётся человеку»), `0008-supported-platforms.md` (платформенный код только в `Storage/IO`)
- **Спецификация формата:** `docs/formats/snapshot.md`

## Контекст

Журнал пишется только в конец и переживает обрыв хвостом (§9 `log-segment.md`). Снапшот так жить не может: он перезаписывает состояние целиком, а значит «частично записанный снапшот» - это не хвост, который можно отбросить, а состояние, которого никогда не было.

Нужен ответ на четыре вопроса:

1. Можно ли выразить «атомарно» через существующий шов файловой системы.
2. Как именно публикуется файл и что видно в каталоге на каждом шаге.
3. Что делать с платформой, где сброс каталога недоступен.
4. Где граница между форматом снапшота и форматом состояния приложения.

## Решение

| Вопрос | Решение |
|---|---|
| Атомарность через шов | Шов расширяется двумя операциями: `RenameAsync` (замена запрещена) и `FlushDirectoryAsync` |
| Публикация | `Create(.tmp)` → запись → `fsync` файла → закрытие → `Rename` → `fsync` каталога |
| Видимость промежуточного | Снапшотом считается только имя `snapshot-{index:D20}.snap`; `.tmp` - не снапшот никогда |
| Осиротевшие `.tmp` | Удаляются при следующем обращении к каталогу: опубликованными они не были |
| Платформа без сброса каталога | `FlushDirectoryAsync` пытается сбросить и продолжает без ошибки, если платформа не умеет; ветвления по ОС в коде нет |
| Формат | Свой заголовок 48 байт с магией-версией `RBSNAP01`, два CRC-32C (заголовок и состояние), состояние - непрозрачные байты приложения |
| Граница с приложением | Хранилище не толкует байты состояния; версия формата состояния - забота `StateMachine` |
| Неверный снапшот | Отказ с причиной; файл не удаляется и не переписывается |

## Обоснование

### Почему шов пришлось расширить

`IStorageFileSystem` (`S1-T03`…`S1-T07`) умел создавать, открывать на дозапись, читать, усекать, удалять и перечислять. Атомарной публикации из этого не собрать: «удалить старый и создать новый» оставляет окно, в котором снапшота нет вовсе, а крах в этом окне означает потерю состояния, которое уже отдано follower-ам.

`Rename` - единственная операция, которая на обеих целевых платформах атомарна в пределах одной файловой системы (`MoveFileEx` без `REPLACE_EXISTING`, `rename(2)`). Замена при этом запрещена сознательно: имена снапшотов уникальны по индексу, и «тихо заменить существующий файл» - это способ потерять валидный снапшот из-за ошибки в вызывающем коде.

`FlushDirectory` нужен потому, что переименование - это изменение каталога, а не файла: без сброса каталога крах после `Rename` может вернуть старое имя. Порядок «сброс файла, затем переименование, затем сброс каталога» - то, что делает результат видимым целиком или не видимым вовсе.

### Почему `.tmp` - это не «почти снапшот»

Соблазн читать `.tmp` при отсутствии основного файла («данные ведь уже записаны») обошёлся бы дорого: `.tmp` не сfsync-ан на момент краха, его длина и CRC не проверены, и восстановление из него - это ровно то гадание, которого формат избегает. Поэтому имя - часть протокола: `.tmp` не читается никогда, а удаляется при первом же обращении к каталогу.

### Почему нет ветвления по ОС

ADR `0008` запрещает `OperatingSystem.*` в `src`, и это не формальность: ветка «на Windows так, на Linux иначе» проверяется только на одной из двух платформ в каждом прогоне гейта. `FlushDirectoryAsync` поэтому не спрашивает платформу, а пытается выполнить операцию: там, где дескриптор каталога не открывается, вызов возвращает «не поддержано» и запись продолжается. Разница платформ описана в формате (`docs/formats/snapshot.md` §7), а не спрятана в коде.

### Почему состояние - непрозрачные байты

`Storage` (ранг 1) не имеет права знать типы `StateMachine` (ранг 3) - это проверяет `LayerReferenceTests`. Поэтому снапшот хранит байты, а не структуру: приложение сериализует состояние само и отвечает за совместимость своего формата. Хранилищу остаётся то, за что оно отвечает: целостность файла, атомарность публикации и выбор актуального снапшота.

## Последствия

- `IStorageFileSystem` вырос на две операции; дубль файловой системы получил их с той же наблюдаемостью (счётчики и точки отказа), поэтому «крах между шагами» проверяется детерминированно.
- `SnapshotStore` не кэширует ничего: актуальный снапшот определяется по каталогу при каждом обращении. Кэш появится по измерению, как и кэш читателей журнала (`0007`).
- Порча снапшота останавливает старт: узел не начинает историю с нуля и не притворяется, что снапшота не было.
- Снапшот больше 1 ГиБ отвергается по длине до чтения в память.

## Чего решение не делает

- Не решает, когда именно сжимать журнал: это `S1-T10`, и пара (лог, снапшот) там же.
- Не сжимает состояние: сжатие - свойство формата состояния приложения, а не хранилища.
- Не гарантирует, что `fsync` каталога произошёл на платформе, где его нет; на Windows остаётся журналирование метаданных NTFS (записано в формате, §7).
- Не восстанавливает повреждённый снапшот из резервной копии: единственная копия состояния - этот файл.

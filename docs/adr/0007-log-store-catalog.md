# ADR 0007. Журнал как каталог в памяти: без кэша читателей, точка коммита в памяти, усечение через писателя

- **Дата:** 2026-10-23
- **Статус:** accepted
- **Задача:** `S1-T06` — `LogStore`: каталог сегментов, append, get, диапазонное чтение, усечение конфликтующего хвоста, retention по снапшоту
- **Опирается на ADR:** `0003-log-segment-format.md` (раскладка и граница файла, отсутствие точки коммита в формате, §4 непрерывность, §7 имя файла, §8 rollover, §9.5 проверки каталога), `0004-durability-policies.md` (шов `IStorageFileSystem`, режимы `fsync`), `0005-log-reading.md` (`SegmentReader` как примитив чтения одного файла), `0006-log-recovery.md` (`SegmentKind`, усечение на месте, отказ как значение)

## Контекст

`SegmentWriter` и `SegmentReader` работают с одним файлом. Журнал Raft — это последовательность записей, которая не кончается на границе сегмента, поэтому `S1-T06` впервые отвечает на вопросы уровня журнала, и каждый из них меняет либо диск, либо API:

1. Что хранится в памяти между операциями: тексты сегментов, разобранные индексы фреймов или только имена и диапазоны.
2. Держать ли читателей открытыми (кэш) или открывать по требованию: `TruncateSuffixAsync` и `CompactAsync` удаляют и укорачивают файлы, а писатель дописывает последний.
3. Кому принадлежит право резать последний сегмент: читателю (`SegmentReader` умеет только читать), писателю (у него открыт дескриптор на запись) или файловой системе.
4. Что делать с точкой коммита: в формате сегмента её нет (`0003`), а инвариант R4 требует не удалять закоммиченное.
5. Как читать запись, которой нет: «ещё не дописана» и «уже сжата снапшотом» оба означают «нет», но решения Raft по ним противоположные.
6. Что считать ошибкой вызывающего при усечении и компакции: отказ или тихое ограничение запроса.

## Решение

| Вопрос | Решение |
|---|---|
| Что в памяти | `List<{BaseIndex, Path}>` — по элементу на сегмент (порядка 16 байт на 64 МиБ файла), плюс `LastIndex`, `LastTerm`, `CommittedIndex`, `SnapshotIndex`. Ни записей, ни индексов фреймов |
| Откуда берутся новые сегменты | Из `SegmentWriter.CreatedSegmentBaseIndexes` после каждого append; каталог на диске повторно не перечитывается |
| Читатели | Открываются на операцию чтения, закрываются в `finally`. Кэша нет |
| Как читается запись | Найти сегмент двоичным поиском по `BaseIndex`, открыть, `ScanAsync`, `ReadAtAsync`, закрыть |
| Усечение последнего сегмента | Писатель закрывается, затем `IStorageFileSystem.TruncateAsync`; после укорачивания создаётся новый писатель через `SegmentWriter.ResumeAsync` |
| Отмена в усечении и компакции | Проверяется один раз до первого разрушающего действия; сами удаления и усечения идут с `CancellationToken.None` |
| Точка коммита | Только в памяти процесса; после старта равна нулю. В файл не пишется (формат её не имеет, `0003`) |
| `MarkCommittedAsync` назад или за конец журнала | Программная ошибка: исключение, а не ограничение значения |
| Усечение закоммиченного | `InvalidOperationException`; неизменяемая граница — `max(CommittedIndex, SnapshotIndex)` |
| Компакция | Удаляются только запечатанные сегменты, целиком покрытые снапшотом. Последний сегмент не удаляется никогда |
| Запись, которой нет | `LogLookupResult` со статусом `Found` / `NotYet` / `Compacted`; `null` не используется |
| Порчи после старта | `InvalidDataException`: файл изменили в обход хранилища. Это не «записи нет» |
| Каталог на диске | Отдельный `SegmentCatalog`: перечисление, порядок, непрерывность, вид сегмента. Один потребитель правил — два (`LogStore` и `S1-T07`) |

## Обоснование

### В памяти — имена и диапазоны, а не содержимое

- Читать запись иначе как с диска нельзя: после старта журнал может быть больше памяти, а `LogStore` не имеет права стать вторым источником правды рядом с файлами. Каталог в памяти — это не данные, а адрес: он отвечает на вопрос «какой файл может содержать индекс», и ответ на него зависит только от базовых индексов.
- Разобранные индексы фреймов (`SegmentReader` уже строит `_frameOffsets`) в памяти не удерживаются намеренно. Стоимость: один последовательный проход на чтение. Выигрыш: усечение и компакция не оставляют за собой устаревших индексов, а расхождение «в памяти столько фреймов, в файле столько» становится невозможным состоянием, а не редким багом. Гипотеза «открытие файла дороже одного прохода» не проверена ничем, поэтому и кэша нет: сначала измерение (`S8-T05` — точка, где это станет видно на нагрузке), потом решение.
- Источник новых сегментов — писатель, а не обход каталога. Rollover случается внутри `AppendAsync`, и знать о нём обязательно до следующего чтения; отдельный `ListFilesAsync` на каждую пачку записей был бы платой в горячем пути за информацию, которая уже есть в памяти у писателя.

### Кэш читателей отвергнут, а не отложен «на потом»

- Открытый читатель живёт на дескрипторе файла, а `TruncateSuffixAsync` удаляет и укорачивает файлы. Кэш обязан инвалидировать запись при каждом удалении, при каждом усечении и при каждом rollover, то есть содержать ровно те правила, ради избежания которых он и заводится.
- На Windows это не стилистика: `SystemStorageFileSystem` открывает файл на запись с `FileShare.Read`, поэтому второй пишущий дескриптор на тот же сегмент не откроется. Усечение последнего сегмента через кэш читателей требовало бы либо закрывать читателя перед каждой записью, либо менять политику разделения файла — то есть решать вопрос уровня формата ради ускорения, которого никто не измерял.
- `FakeStorageFileSystem` разницу не моделирует (там дескрипторы не конфликтуют), поэтому «зелёный тест с кэшем» ничего бы не доказывал: проверка на дубле была бы права, а поведение на Windows — нет. Это второй довод против кэша, независимый от первого.

### Усечение идёт через писателя, а не мимо него

- Последний сегмент дописывает писатель, и он единственный знает свою позицию и последнюю запись. Резать файл, пока писатель держит дескриптор, значит получить либо отказ разделения (Windows), либо запись в удалённый inode (Unix).
- Поэтому порядок зафиксирован кодом: закрыть писателя → удалить сегменты выше точки обрезки → усечь или удалить оставшийся → создать нового писателя на `SegmentResumeState` из уцелевшей записи. Писатель продолжает с того же места, с каким и закрылся бы, поэтому проверки непрерывности (§4) остаются ровно теми же, что при старте.
- Отмена после первого разрушающего действия не проверяется. Полуобрезанный журнал хуже необрезанного: его нельзя ни продолжить, ни восстановить без потери того, что уже было удалено. Один `ThrowIfCancellationRequested` до начала — единственная точка отказа.
- Усечение закоммиченного — исключение, а не «обрежем сколько можно»: R4 нарушается молча, если вызывающий ошибся в арифметике, и узнает он об этом не тогда, когда это ещё можно исправить. Неизменяемая граница берётся как `max(CommittedIndex, SnapshotIndex)`: записи, вошедшие в снапшот, тем более не удаляются из журнала задним числом.

### Точка коммита живёт в памяти, и это записано, а не подразумевается

- В формате сегмента точки коммита нет (`0003`), а вывести её из диска нельзя: после рестарта неизвестно, какие записи были подтверждены, — это знание Raft, и оно приходит извне (`AppendEntries` лидера, `S1-T07`).
- Значит `CommittedIndex` в `LogStore` — ловушка для ошибки вызывающего внутри одного запуска, а не хранилище гарантии R4. Это записано в XML-doc `ILogStore.MarkCommittedAsync`, чтобы никто не прочитал поле как «журнал знает, что закоммичено».
- Дописывать значение на диск в обход формата (отдельный файл, поле в заголовке) нельзя без новой версии формата и ADR: §3 фиксирует заголовок, а `0003` явно оставил точку коммита вне его.

### Отсутствие записи — три состояния, а не два

- Raft обрабатывает «индекса ещё нет» и «индекс уже сжат» противоположным образом: первое — продолжать репликацию со следующего индекса, второе — отправить `InstallSnapshot` (`S3-T02`). Если `GetAsync` возвращает `null`, вызывающий обязан восстановить различие из `FirstIndex`, и первая же забытая проверка отправит снапшот вместо продолжения (или наоборот).
- Поэтому различие вынесено в контракт (`LogLookupStatus`), а не в комментарий: компилятор заставляет обработать оба случая.
- Порча файла после успешного старта — не «записи нет»: это `InvalidDataException`. Иначе испорченный диск выглядел бы как обычное отставание реплики, и узел молча продолжил бы работу с дырой в журнале.

### Правила каталога — в одном месте

- «Какие файлы образуют журнал» нужно двум потребителям: открытию хранилища и восстановлению при старте (`S1-T07`). Две копии одной нормы разъезжаются на первом же уточнении формата, поэтому перечисление, сортировка, проверка имени (§7), непрерывности (§4) и пустого сегмента (§8) вынесены в `SegmentCatalog`.
- Каталог ничего не чинит: он возвращает `Truncated` (оборван только последний сегмент — работа восстановления) или `Corrupt` (структурное нарушение — старт запрещён). Это то же разделение, что в `0006`, но на уровне всего журнала.
- Читателей каталог не держит: сегмент открывается, сканируется и закрывается в `finally` на всех путях, включая отказ. Иначе восстановление не смогло бы усечь последний сегмент на Windows, а отчёт о старте зависел бы от того, сколько дескрипторов осталось висеть.

## Последствия

- `S1-T07` получает каталог как готовую операцию: ему остаётся вызвать `SegmentRecovery` для последнего сегмента, собрать отчёт и решить, что делать с запечатанными. Проверки §9.5, которые принадлежат всему журналу, он не повторяет.
- Чтение стоит одного `open` и одного последовательного прохода по файлу. Если `S8-T05` покажет, что это дорого, кэш появится новым ADR с измерением в обосновании — но не раньше. Место для него подготовлено: весь доступ к сегментам идёт через `LogStore.OpenScannedAsync`.
- `SegmentWriter` публикует `CreatedSegmentBaseIndexes` — список базовых индексов созданных им сегментов. Это единственный канал «случился rollover», и он же заменил бы перечитывание каталога, если оно когда-нибудь понадобится.
- `SegmentWriter` помечается непригодным (`_broken`), если rollover не завершился: запечатанный сегмент уже сброшен на устройство, а активного файла нет. Продолжать молча нельзя, следующий append обязан упасть с понятной причиной.
- `ILogStore.GetAsync` возвращает `LogLookupResult`; `LogRecord?` больше не используется. `CompactAsync` принимает `LogIndex`, а не `SnapshotMetadata`: хранилище не имеет права зависеть от типа состояния машины (ранги слоёв: Storage 1, StateMachine 3).
- Память на журнал: ~16 байт на сегмент плюс строка пути. При 64 МиБ на сегмент это меньше тысячной доли объёма данных.
- Цена отказа от кэша — повторное сканирование сегмента на каждое чтение. Она видна в тестах (`ReadCount` дубля) и станет предметом измерения, а не догадки.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Кэш открытых `SegmentReader` (1–2 штуки) | Инвалидация на каждом удалении, усечении и rollover; на Windows открытый писатель и второй пишущий дескриптор конфликтуют; дубль эту разницу не моделирует, то есть тест был бы зелёным и неправым |
| Кэш разобранных индексов фреймов в памяти | Устаревает при усечении и rollover; расхождение «в памяти столько, в файле столько» становится возможным состоянием; выигрыш не измерен |
| Кэш записей (LRU) | Journal Raft читается в основном последовательно и один раз; попадание в кэш дороже самого чтения |
| Полный каталог на диске перечитывать после каждого append | Обход каталога в горячем пути ради информации, которая уже есть у писателя |
| Резать последний сегмент читателем или файловой системой напрямую | Писатель держит дескриптор: на Windows отказ, на Unix запись в удалённый inode |
| Продолжать писать в усечённый файл старым писателем | Его `CurrentSegmentSize` и `LastIndex` разошлись с файлом; состояние пришлось бы править извне, в обход проверок `ResumeAsync` |
| Проверять отмену между удалениями в `TruncateSuffixAsync` | Полуобрезанный журнал: часть сегментов удалена, часть нет, и восстановление не знает, что было задумано |
| `CompactAsync(SnapshotMetadata)` | Тип состояния машины живёт на ранге 3, хранилище — на ранге 1; зависимость вверх запрещена архитектурным тестом |
| Точка коммита в отдельном файле | Новый формат на диске и новая версия совместимости ради значения, которое Raft восстанавливает из сети; `0003` оставил её вне заголовка осознанно |
| Тихий `CommittedIndex` при усечении закоммиченного | R4 нарушается молча; вызывающий узнаёт о своей ошибке тогда, когда исправить уже нечего |
| `GetAsync` возвращает `LogRecord?` | Три состояния сводятся к двум, и различие «ещё нет» / «сжато» восстанавливает вызывающий — то есть забывается |
| Удалять последний сегмент, если он покрыт снапшотом | Журнал остаётся без активного файла, а `prevLogTerm` для следующей записи брать неоткуда |
| Правила каталога внутри `LogStore` | Второй потребитель — `S1-T07`; две копии нормы разъезжаются при первом уточнении |

# S1 - Долговечный лог и снапшоты

## For future agent

Спецификация этапа S1 проекта (см. `README.md`): собственное долговечное хранилище для журнала Raft - append-only сегменты с CRC32C, индекс сегментов, восстановление после оборванной записи (torn write) и атомарные снапшоты. Этап полностью тестируем без сети и без знания об очереди: на входе список записей журнала, на выходе гарантия "записанное и засинканное переживает падение процесса и машины". Задачи `S1-T01`..`S1-T10` в `tasks/README.md`; этап проверяет инвариант R6 (durability голосования) в паре с S2-T02 и закладывает основу для R4 (отставший follower догоняет через снапшот).

**Состояние 2026-09-30:** `S1-T01` закрыт. Канонический текст формата - `docs/formats/log-segment.md` в репозитории (коммит `db07b48`), обоснования решений - `docs/adr/0003-log-segment-format.md`; открытые решения этапа 1 и 2 закрыты. `S1-T02` закрыт (коммит `f59920b`) - кодек записи, фрейма и заголовка, своя CRC-32C и property-тесты FsCheck. `S1-T03` закрыт (коммит `0f74acb`) - `SegmentWriter` с тремя политиками fsync и rollover по размеру, шов файловой системы `IStorageFile`/`IStorageFileSystem` и дубль `FakeStorageFileSystem`; открытое решение 4 (интервал `Periodic`) закрыто ADR `docs/adr/0004-durability-policies.md`. `S1-T04` закрыт (коммит `01fb634`) - `SegmentReader` с итерацией вперёд и назад без полной загрузки сегмента, индекс смещений, вердикт о хвосте (`TailProblem` с `ValidEndOffset` вместо «усечь/отказать») оставлен восстановлению; открытое решение 6 закрыто ADR `docs/adr/0005-log-reading.md`. `S1-T05` закрыт (коммит `9eb1096`) - восстановление сегмента: оборванный хвост последнего сегмента усекается на месте, недописанное создание удаляется, нечитаемый заголовок последнего сегмента и любая порча (в том числе в запечатанном) останавливают старт без единой разрушающей операции; краш-тест убивает отдельный процесс-жертву; открытое решение 7 закрыто ADR `docs/adr/0006-log-recovery.md`; добавлен 14-й проект `tests/RaftBroker.CrashHarness` (записан в `tasks/README.md`). Следующая задача - `S1-T06` (`LogStore`: индекс сегментов в памяти, `Append`, `Get`, `TruncateSuffix`, диапазонное чтение, retention по снапшоту).

## Цель этапа

1. Формат сегмента описан побайтово и не меняется без миграции.
2. Любое частичное повреждение (torn write) обнаруживается CRC и приводит к детерминированному усечению до последней валидной записи, а не к падению с неясной ошибкой.
3. Снапшот либо существует целиком, либо не существует: промежуточных состояний, читаемых как валидный снапшот, нет.
4. Компакция лога не создаёт "дыру": либо доступна вся история, либо снапшот плюс хвост лога.

## Что НЕ входит

- Логика Raft: ни term-переходы, ни выборы, ни правило коммита. `LogStore` ничего не знает про роли.
- Сжатие (gzip/zstd) записей и снапшотов. Отложено: сначала корректность, потом объём.
- Шифрование данных на диске. Вне границ проекта.
- Вынесение payload в отдельные blob-файлы. **Закрыто 2026-09-28:** владелец выбрал in-line хранение (открытый вопрос 6 в README.md); первая версия хранит payload в самой записи журнала с лимитом 1 МБ и понятной ошибкой при превышении. Вынос в blob-файлы остался возможным расширением при больших сообщениях.
- Асинхронный I/O через `RandomAccess`/io_uring как оптимизация: корректность важнее в этом этапе.

## Формат сегмента (финализирован в S1-T01)

```
Segment file:
  [Header]  magic "RBSEG001", format version (u16), segment base index (i64), created at (i64)
  [Frame]*  frameLength (u32) | recordType (u8) | term (i64) | index (i64) | payload (bytes) | crc32c (u32)
  ---
  crc32c считается по recordType..payload включительно
  frameLength не включает поле frameLength и поле crc32c
  Порядок записей: index строго возрастает на 1 внутри сегмента
```

**Канонический текст - `docs/formats/log-segment.md` в репозитории (S1-T01)**; обоснование решений - `docs/adr/0003-log-segment-format.md`. Блок выше оставлен как история эскиза. Что уточнено относительно него: заголовок 30 байт с `headerCrc32c`, магия `RBSEGLOG` без версии (версия только в `formatVersion`), границы `frameLength` 17..1 048 593, закрытая таблица `recordType`, имена `{baseIndex:D20}.seg`, обязательный порядок rollover (fsync старого сегмента, затем fsync заголовка нового, затем запись фрейма), проба продолжения для отличия torn write от порчи в середине и правило «запечатанный сегмент всегда полон».

Правила, которые обязаны попасть в спецификацию:

1. Версия формата читается первой; неизвестная версия - отказ, а не "попробуем прочитать как получится".
2. Неполный последний фрейм (меньше `frameLength` байт) - признак torn write: усечение до начала этого фрейма.
3. Несовпадение CRC в середине сегмента - не torn write, а порча: отказ с диагностикой позиции. Автоматическое усечение здесь запрещено (иначе молча теряется закоммиченная история).
4. Запись `frameLength = 0` запрещена.
5. Сегмент именуется по base index и не переименовывается после создания.
6. Таблица типов записей (`recordType`) включает как минимум: команду state machine, `no-op` запись лидера (S2-T06) и `config` (изменение состава, S7-T02). S1 не разбирает payload записи `config`: тип нужен только чтобы хранилище и снапшоты не теряли такие записи и чтобы apply-loop мог их отличить.

## Контракты этапа

```csharp
public interface ILogStore
{
    LogIndex FirstIndex { get; }          // с учётом снапшота: начало доступной истории
    LogIndex LastIndex { get; }
    Term LastTerm { get; }
    LogIndex CommittedIndex { get; }      // ниже этого индекса записи неизменяемы

    ValueTask AppendAsync(IReadOnlyList<LogRecord> records, DurabilityMode mode, CancellationToken ct);
    ValueTask<LogRecord?> GetAsync(LogIndex index, CancellationToken ct);
    ValueTask<IReadOnlyList<LogRecord>> ReadRangeAsync(LogIndex from, int maxCount, CancellationToken ct);
    ValueTask TruncateSuffixAsync(LogIndex from, CancellationToken ct);   // удаляет index >= from
    ValueTask CompactAsync(SnapshotMetadata snapshot, CancellationToken ct);
}

public enum DurabilityMode { PerEntry, GroupCommit, Periodic }

public interface ISnapshotStore
{
    ValueTask<SnapshotMetadata?> GetLatestAsync(CancellationToken ct);
    ValueTask WriteAsync(SnapshotMetadata metadata, ReadOnlyMemory<byte> state, CancellationToken ct);
    ValueTask<ReadOnlyMemory<byte>> ReadStateAsync(SnapshotMetadata metadata, CancellationToken ct);
    ValueTask DeleteOlderThanAsync(LogIndex index, CancellationToken ct);
}
```

Правило: `TruncateSuffixAsync(from)` разрешён только при `from > CommittedIndex`. Попытка обрезать закоммиченную историю - программная ошибка и обязана бросать исключение, а не молча усекать.

## План тестов этапа

| Тип | Что проверяется | Инвариант | Задача |
|---|---|---|---|
| Property-based | round-trip 10 000 случайных записей; битый CRC отвергается | - | S1-T02 |
| Crash-тест | обрыв записи на каждом байте последнего фрейма; восстановление детерминировано | R6 (основа) | S1-T05 |
| Crash-тест | процесс убит между `temp`-записью и `rename`, между `rename` и `fsync` каталога | Q7 (основа) | S1-T09 |
| Стресс-тест | параллельные append и read при трёх fsync-политиках | - | S1-T03, S1-T08 |
| Модульный | границы сегментов, пустой сегмент, запись точно в конец | - | S1-T04 |
| Модульный | отказ при порче в середине сегмента и запрет обрезки закоммиченного | R4 (основа) | S1-T05, S1-T06 |
| Интеграционный | компакция плюс одновременная запись, восстановление после краха в каждой точке | R4, Q7 | S1-T10 |

Имитация краха реализуется двумя способами: (1) фабрика файловой системы, падающая на заданной операции, (2) реальное завершение процесса в дочернем `dotnet`-процессе. Второй способ обязателен хотя бы для одного сценария каждого типа, иначе остаётся риск, что имитация не соответствует реальному `fsync`-поведению. Для `S1-T05` он реализован: жертва - отдельный проект `tests/RaftBroker.CrashHarness`, тест убивает её снаружи и только потом восстанавливает сегмент.

## Чек-лист ревью R1

1. Формат зафиксирован так, что сторонний разработчик восстановит лог по документу, без чтения кода?
2. Torn write отличается от порчи в середине, и поведение для этих случаев разное? Это проверено тестами?
3. `DurabilityMode` действительно влияет на вызов fsync, а не только на комментарий? fsync подтверждён наблюдением (например, счётчиком вызовов)?
4. `TruncateSuffixAsync` защищён от обрезки закоммиченной истории?
5. Снапшот после краха в каждой точке записи читается либо старым, либо новым, но никогда "частично новым"?
6. Компакция не удаляет записи, нужные отставшему follower, которого ещё не догнал снапшот?
7. Индекс сегментов перестраивается сканированием, а не берётся из доверенного файла? Что будет, если файл индекса испорчен?
8. Модель конкурентности объяснима одной фразой ("один писатель, читатели не блокируют") и это видно в коде?

## Открытые решения этапа

1. **РЕШЕНО 2026-09-30 (S1-T01):** сегмент 64 МиБ (67 108 864 байт), значение конфигурируемо, но формат от него не зависит; rollover только на границе записи; обязательный порядок - fsync старого сегмента, затем создание и fsync заголовка нового, затем запись фрейма. См. `docs/formats/log-segment.md` §8, ADR `0003-log-segment-format.md`.
2. **РЕШЕНО 2026-09-30 (S1-T01):** индекса сегментов на диске в версии 1 нет - индекс перестраивается сканированием при старте. Кэш-файл отвергнут как второй источник истины; если появится позже, то только как недоверенный ускоритель с проверкой по сегментам. См. ADR `0003-log-segment-format.md`.
3. **РЕШЕНО 2026-09-28 (владелец): payload in-line с жёстким лимитом 1 МБ** на запись и понятной ошибкой при превышении (открытый вопрос 6 в README.md). Согласуется с лимитом сообщения gRPC в S4 и валидацией в S5-T02.
4. **РЕШЕНО 2026-09-30 (S1-T03):** `PerEntry` - эталонный режим для тестов durability (fsync на каждую запись); `GroupCommit` - по умолчанию (один fsync на вызов `append`, возврат только после fsync); `Periodic` не вызывает fsync в append вовсе (долговечность даёт явный `FlushToDiskAsync`), таймера внутри писателя нет - интервал и расписание принадлежат актору `S1-T08`, ориентир порядка 10 мс уточняется измерением в `S8-T05`. `Periodic` запрещён на commit-пути Raft. См. ADR `0004-durability-policies.md`.
5. **Решение 2026-09-28 (вопрос 5):** подтверждённая запись обязана пережить падение (модель отказов не ослабляется). Любой режим, который отвечает клиенту до fsync, запрещён для commit-пути; это проверяется тестом на вызовы fsync, а не комментарием.
6. **РЕШЕНО 2026-09-30 (S1-T04):** читатель хранит в памяти только индекс смещений фреймов, а не записи; хвост с повреждением/обрывом - `TailProblem` с `ValidEndOffset` (координата, не вердикт), судьбу хвоста решает `S1-T05`; структурные отказы - результат, не исключение; шов ввода-вывода разделён на пишущий и читающий интерфейсы; проба продолжения §9.5 шаг 5 - примитив читателя (`ReadFrameAtAsync`/`ReadFrameLengthAsync`), решение по ней - у восстановления. См. ADR `0005-log-reading.md`.
7. **РЕШЕНО 2026-09-30 (S1-T05):** восстановление само решает и само действует; вид сегмента (`Sealed`/`Last`) - вход, потому что по одному файлу «оборванный хвост последнего сегмента» и «порча» неразличимы. Оборванный хвост последнего сегмента усекается **на месте** (`TruncateAsync`, только уменьшение, fsync метаданных); файл короче заголовка в последнем сегменте **удаляется** (подтверждённых записей там быть не может, валидным он не станет никогда); нечитаемый заголовок последнего сегмента - отказ с сохранением файла, а всё, что не сходится в запечатанном сегменте или имеет продолжение за повреждением, - отказ по §9.4 без единой разрушающей операции. Проба продолжения проверяет только структурную целостность фрейма на `p + 4 + L + 4`; проверка непрерывности индексов в ней отвергнута как превращающая порчу в усечение (§9.6). Реальный краш проверяется отдельным процессом-жертвой `tests/RaftBroker.CrashHarness` (14-й проект решения, ранг 98 в таблице слоёв). См. ADR `0006-log-recovery.md`.
